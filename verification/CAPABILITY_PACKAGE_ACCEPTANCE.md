# Capability Package Acceptance

Capability Packages are accepted through real outcomes, not package-level conformance ceremonies.

For a concrete workload, record only the evidence necessary to answer:

1. **Problem/target** — what real result was required?
2. **Applicable knowledge** — which mature standards, methods or professional practices governed the work?
3. **Selected capabilities** — which Skills, tools, services, agents or humans were used, and why were they sufficient?
4. **Target validation** — what domain/native/real-world evidence demonstrates success or remaining failure?
5. **Gap disposition** — did the task reveal a repeated missing capability worth adding, or only a one-off task-local need?

## Standing vocabulary

- `READY_FOR_REAL_WORK`: enough capability exists to attempt normal workloads; additional tools remain on-demand.
- `TASK_GAP`: one current real workload has a concrete missing capability.
- `BLOCKED`: the current workload cannot proceed safely/correctly with available mature options.
- `NEXT_CENSUS`: package has not yet received the current census treatment.

Do not use `COMPLETE` for an open-ended domain ecosystem. A mature package is one that reliably knows how to select external knowledge/capabilities and verify real outcomes without recreating the field.
