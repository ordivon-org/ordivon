# Security v2 technology selection R2

Date: 2026-09-12
Status: selected architecture baseline; selection is not installation or production-admission evidence.

## Goal

Security v2 is not a monolithic security platform. It composes mature external security systems across the software-security lifecycle and retains only the Ordivon-specific semantic waist needed to bind exact subjects, evidence, authority, admission, and verified consequence.

The lifecycle target is:

`MODEL -> PROTECT SOURCE -> BUILD -> VERIFY -> ATTEST -> ADMIT -> OBSERVE -> DETECT -> RESPOND -> RECOVER -> PROVE`

A provider is admitted only when it closes a distinct lifecycle gap. Duplicate scanners or infrastructure are not added merely for category completeness.

## P0 additions

### 1. TM-BOM + OWASP Threat Dragon

Use the OWASP Threat Model Library JSON schema (TM-BOM direction) as the canonical machine-readable threat-model artifact. Threat Dragon is the preferred human editor/viewer, not the authority format. This keeps the model portable when the UI/provider changes.

Threat Dragon 2.6.2 can read/import TM-BOM-oriented library models, while its native v2 format remains tool-specific and its documented long-term direction is TM-BOM. Security therefore validates the canonical artifact against an exact external schema tag/digest and separately binds the model to an exact architecture envelope.

Security v2 does **not** create an `OrdivonThreatOntology`. CAPEC/CWE identifiers may be referenced where useful, while project-specific threats remain ordinary model content.

Required acceptance before production use:

- model file is version-controlled or digest-bound;
- exact subject architecture/source revision is recorded;
- threats map to mitigations and at least one verification path where applicable;
- changed architecture can make old threat evidence stale rather than silently current.

### 2. OpenSSF Scorecard

Use Scorecard as a repository/security-posture evidence provider for branch protection, CI tests, code review, pinned dependencies, token permissions, signed releases and similar source/repository controls.

Do not use `scorecard score >= N` as the Security authority rule. The aggregate score contains assumptions that may not fit a single-maintainer or non-public repository. Security should consume named checks plus applicability metadata and let OPA decide the admission policy.

### 3. OWASP ZAP Automation Framework

Use the Automation Framework instead of custom web scanner orchestration. ZAP provides spidering, passive/active scanning, authentication support, and OpenAPI/SOAP/GraphQL jobs.

Active scanning is an effectful action. It therefore requires:

- exact target identity;
- explicit authority for the target;
- declared scan profile;
- bounded environment or explicit external authorization;
- provider output retained without normalization into a proprietary finding schema.

The preferred execution shape is an ephemeral target created by the owning E2E/Runtime, followed by a ZAP plan and independent target cleanup/readback.

### 4. ClusterFuzzLite

Use ClusterFuzzLite as the default CI continuous-fuzzing coordinator. It supports short code-change fuzzing, longer batch fuzzing, corpus maintenance and coverage reporting. Underlying engines/sanitizers remain external.

OSS-Fuzz is optional for eligible public open-source projects; it is not required by Security v2 itself.

Security v2 retains only bindings from a crash/finding to exact revision/build/fuzz target and the evidence required for admission or remediation.

### 5. SLSA v1.2 Build Provenance

The current VSA answers what Security verification concluded. Build provenance answers how the artifact was produced. Both are required for a mature supply-chain path.

The artifact/build owner must emit SLSA build provenance for an exact output. Security verifies the provenance, subject digest, builder identity/policy and expected build definition. Security must not synthesize provenance after the fact from incomplete local observations.

## P1 addition: runtime detection

### Falco selected as baseline

Falco is selected as the default runtime-security detection provider because its primary role is to consume runtime event streams, evaluate rules and emit alerts. That maps cleanly to the Security ownership model:

`Falco observation -> digest-bound evidence -> Security applicability/standing -> optional incident workflow`

Falco does not become world-truth authority and does not automatically execute remediation.

Current host preflight on 2026-09-12:

- WSL2 Linux `6.6.123.2-microsoft-standard-WSL2`;
- x86_64;
- `/sys/kernel/btf/vmlinux` present;
- `/sys/fs/bpf` exists but bpffs was not mounted at observation time;
- Falco is not currently installed.

A real modern-eBPF smoke is required before host admission.

### Why Tetragon is not the default

Tetragon provides both eBPF observability and kernel-level enforcement. That is useful where inline enforcement is a real requirement, but enabling it by default would introduce another physical-effect authority beside Runtime/host policy. Therefore Tetragon remains conditional rather than being installed merely for feature completeness.

If a future consumer requires inline enforcement, the differential must prove:

- exact policy identity and revision;
- authority to enforce on that host/workload;
- observation versus enforcement-result separation;
- failure/recovery behavior;
- no silent bypass of Runtime/Operations ownership.

## Explicit non-selections

The following are intentionally **not** added to the baseline now:

- a new proprietary finding database or unified `OrdivonFinding` schema;
- a generic Ordivon threat ontology;
- an additional IaC scanner while Trivy covers the admitted requirement;
- both Falco and Tetragon for the same baseline runtime-detection role;
- a SIEM/Elastic/Splunk/Wazuh deployment without an observed correlation/retention requirement;
- Kubernetes merely to obtain Kubernetes security tooling;
- Security-owned secret storage when OpenBao or another mature secret authority can be Operations-owned;
- custom fuzz engines;
- custom web scanner/crawler;
- custom VM lifecycle or signing primitives.

## Ownership composition

```text
Engineer / product owner
  -> architecture + source + tests
  -> Threat Dragon model / security requirements

Artifact / CI / build owner
  -> exact build
  -> SBOM
  -> SLSA Build Provenance

External verification providers
  -> Gitleaks / Semgrep / OSV / Trivy / Syft
  -> Scorecard
  -> ZAP
  -> ClusterFuzzLite
  -> Falco

Security v2 semantic waist
  -> exact subject
  -> evidence digest/currentness/applicability
  -> authority and admission
  -> verified consequence / security standing
  -> in-toto + SLSA VSA verification

Operations / Runtime / Temporal
  -> services and credentials
  -> physical execution
  -> durable remediation/incident workflows
```

## Migration order

1. Record and test Threat Dragon model binding without inventing new threat ontology.
2. Add Scorecard as repository-posture evidence and test per-check applicability.
3. Add ZAP against a deliberately local/ephemeral authorized target; prove active-scan authority fencing.
4. Add one real ClusterFuzzLite target and retain a deterministic crash/non-crash evidence contract.
5. Add/verify real SLSA Build Provenance from an existing Artifact build.
6. Only after the static/build path is green, test Falco modern-eBPF observation on the current WSL2 host.
7. Continue the already-open Packer -> image -> libguestfs independent-readback VM closure.

This ordering closes distinct lifecycle gaps while keeping the Security-owned code surface small.
