# Runtime introduction production plan

This plan is derived from the Runtime implementation bound in `production.json`, not from a generic product-video template.

## The one proof

The film proves one bounded property:

> After delivery becomes uncertain, one admitted operation retains a stable recorded Job identity, can be recovered without blindly admitting a second Job, exposes bounded execution evidence, and can close only the exact Workspace state that was reviewed.

It does not try to explain cancellation, backup/restore, deployment, Windows execution, repair, or every Runtime tool.

## Executable proof source

The selected proof is generated by Runtime-owned:

```text
scripts/demo_runtime_flow.py
examples/runtime-demo/
```

The demo targets the installed Runtime MCP service, creates a temporary deterministic source fixture, performs a guarded Patch, admits one three-step execution, recreates the client, replays the exact request, recovers/observes the recorded Job, reads terminal evidence, verifies a one-file diff, and compare-and-closes the exact reviewed source state. Credentials and private Runtime paths are excluded from the Receipt.

The current selected Receipt is `evidence/runtime-demo.receipt.json`, exact digest `sha256:c612500db2312fc956e0b9dc801853aab3ae31f7f182f3cce6a7649c02ccdbe1`.

## Presentation decision

Runtime’s public product surface is MCP/service execution, not a presentation-oriented terminal CLI. Therefore the picture master no longer requires staged “real terminal” footage as the proof carrier.

Instead:

- Runtime-owned live execution produces the exact Receipt;
- Studio renders **receipt-derived evidence views** for selected Patch/Job/Attempt/observation/evidence/diff facts;
- those views are explicitly labeled `receipt-derived evidence view · not a terminal capture`;
- problem framing and current-product boundary scenes are explicitly labeled as Studio explanatory/current-authority framing;
- the existing RuntimeFlow, RequestReplay, and ExactClose compositions remain programmatic explanations of source-bound facts.

This preserves provenance better than inventing a terminal UI Runtime does not own.

## Remaining acceptance before approval

1. produce/select narration audio from the locked script;
2. register exact audio bytes and provenance;
3. assemble picture + audio;
4. continuously playback-audit pacing, readability, cuts, and audio-image implication;
5. run final delivery QC;
6. choose `approved` or `revise`.

No new workflow engine, approval database, or generic critic is required for that gate.
