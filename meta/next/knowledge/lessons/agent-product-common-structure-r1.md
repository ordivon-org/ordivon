## Scope

This synthesis is scoped to the studied family of coding Agents, IDE Agents, autonomous/cloud software Agents and app-building Agents represented by the campaign.

It is **not** an industry-wide prevalence claim and **not** a universal ontology for every possible Agent system.

Eight substantive independent reports were recovered. A02 and A05 were not retrieved and remain explicit gaps.

## Promotion rule

A candidate common primitive is promoted only when it has:

1. support from at least two independent recovered product-family reports;
2. support from at least one recovered mechanism-role report;
3. no fatal falsifier from B05;
4. a natural owner that does not require Ordivon to duplicate a mature provider.

Corpus frequency alone is never sufficient.

# 2. Primitive: Context / Instruction Compiler

Standing: **STRONG_COMMON**

Evidence:

- A01: lazy capability/context loading, soft context, model routing, Skills/plugins;
- A04: project/design context is first-class in app-building loops;
- B02: direct mechanism study identifies typed compilation, precedence, scoping, progressive disclosure, model-specific lowering and compaction;
- B05: runtime-assembled/layered context survives falsification.

The effective model input is better described as a compilation result than as one permanent Prompt string:

```text
model/provider policy
+ task/product context
+ current mode
+ admitted Tools
+ scoped project instructions
+ Skills/procedures
+ explicit current state
+ selected history/memory
+ context budget
→ effective model view
```

## Natural owner

```text
Host/application/caller policy
+ Provider/Adapter lowering
+ Harness only for bounded Run cognition mechanics where durability is required
```

Do **not** create a universal Ordivon mega-prompt or global context ontology.

# 3. Primitive: Typed Action / Tool Surface

Standing: **STRONG_COMMON**

Evidence:

- A01: canonical Tool registry;
- A03: broad scoped effect interfaces across shell/browser/deploy/database/secrets/SaaS;
- A04: inspect/edit/runtime/preview/integration/VCS/deploy effect classes;
- B01: semantic effect classes are more stable than Tool names;
- B03: Tool registry is a recurring loop primitive;
- B05: typed action surface survives falsification.

The stable commonality is **not the exact Tool list**.

The stable structure is:

```text
model sees bounded action affordance
→ emits action intent
→ host/provider validates shape/authority
→ external owner executes
→ structured observation returns
```

## Minimal software-Agent effect waist

B01's strongest practical minimum is:

```text
observe/read/search
+ structured mutation
+ general execution
+ returned observation
```

This is a software-Agent waist, not a universal all-domain ontology.

## Natural owner

- native provider Tool registries;
- MCP when interoperability is useful;
- direct API/CLI where mature and simpler;
- Runtime only for exact physical-effect/evidence boundaries it uniquely owns.

# 4. Primitive: Model Decision + Observation-Driven Control Loop

Standing: **STRONG_COMMON**

Evidence:

- A01: reason → act → observe;
- A03: observation/evaluation loop over durable sessions;
- A04: intent → context → mutation → preview → observation → publication;
- B01: observe → mutate/execute → verify;
- B03: explicit context → inference → effect → execute → observation → state update → continue/complete;
- B05: action → execution → observation survives red-team review.

The common structure is therefore not a fixed ReAct prompt template. It is an **observation-driven closed loop**.

Different products may compress multiple steps into code, parallel Tools, subagents, streamed artifacts or provider-native continuation.

## Natural owner

- Agent provider / Harness for one bounded Run's loop mechanics;
- caller/domain for cross-Run strategy and semantic objective;
- Temporal/workflow system for long-lived cross-Run orchestration when needed.

# 5. Primitive: Explicit Working / Control State Separate from Transcript

Standing: **STRONG_COMMON_WITH_VARIATION**

Evidence:

- A01: structured task state plus persistent soft context;
- A03: durable task/session lifecycle;
- A04: project state, checkpoints/version history and publish standing;
- B02: transcript/event history is distinct from explicit current world state; compaction preserves canonical current state;
- B03: plans, modes, approvals and sessions/tasks appear as explicit runtime state.

The commonality is **state separation**, not one universal schema.

Possible state includes:

```text
current task/session
working set
mode
plan/todo
approval standing
project/version
current environment
provider continuation identity
```

but each belongs to its natural owner.

## Natural owner

- domain/product state: domain/application;
- bounded current cognition: Harness where durability is required;
- durable workflow state: Temporal;
- physical execution state: Runtime/provider;
- conversation/provider state: provider.

Do not duplicate them into a global Ordivon state object.

# 6. Primitive: Authority / Effect Gate Outside Prompt Text

Standing: **STRONG_COMMON**

Evidence:

- A01: Prompt policy separated from permissions/hooks/sandbox/worktree isolation;
- A03: credential/effect interfaces, RBAC, typed confirmations and commit gates;
- A04: permission modes and publish/deploy effect boundary;
- B03: authority/approval sits between proposed effect and execution;
- B04: dedicated study explicitly distinguishes capability visibility, authorization, environmental confinement, credentials/network mediation and effect validation;
- B05: externalized authority survives falsification.

Canonical distinction:

```text
Prompt rule
!= Tool visibility
!= Permission
!= Credential authority
!= Sandbox/isolation
!= Effect truth
```

Mandatory approval is **not** a common primitive. Approval is one possible policy mechanism applied according to effect class, risk, caller policy and environment.

## Natural owner

- IAM / policy engine / caller-domain delegation;
- provider-native permission controls;
- OS/container/sandbox/resource boundaries;
- Runtime/provider effect admission;
- external service/domain for final occurrence truth.

Prompt text may advise behavior but must not be the enforcement root.

Standing: **STRONG_COMMON**

- A03: owned VM/sandbox/project substrate is central;
- A04: Vercel Sandbox/WebContainer/project preview runtime;

An Agent product requires somewhere actions become real:

```text

container
VM
browser
cloud sandbox
external API

```

The exact substrate is not common; the **separation between model decision and physical execution** is.

## Natural owner

Prefer mature execution providers:

- OS/container/VM/cloud sandbox;
- Browserless/Playwright for browser work;
- Temporal for durable workflow;
- Runtime for exact local physical commitment/evidence where justified;
- domain-specific provider APIs for native effects.

# 8. Primitive: Verification / Feedback

Standing: **STRONG_COMMON**

Evidence:

- A01: Tool-result feedback, LSP, lint/check hooks, stop-hook continuation, plugin eval;
- A03: observation/evaluation and commit/release gates;
- A04: preview, screenshots, lint/runtime errors, browser feedback, publish checks;
- B01: verification-by-reexecution/observation;
- B03: tests/checks/hooks/checkpoints/retrieval evidence;
- B04: act → observe → repair using diagnostics/diffs/checkpoints/human review where appropriate;
- B05: verification survives red-team review.

The common principle is:

> **Action is not completion. External observation feeds the next decision.**

Verification can be mechanical, behavioral, domain-specific or human-sourced depending on the claim.

## Natural owner

- tool/provider for direct execution observations;
- OpenTelemetry for telemetry only;
- test/build/lint/browser/eval providers for mechanical checks;
- domain V&V for semantic acceptance;
- Human only when the claim actually requires human evidence.

`span OK`, process exit zero or Agent self-report never equals domain truth by itself.

# 10. Explicitly rejected universals

The parallel study is useful partly because it rejects several seductive abstractions.

## 10.1 One Tool per turn — REJECTED

Parallel calls, code-execution compression, Tool programs and subagent delegation invalidate it.

## 10.2 Mandatory human approval — REJECTED

Approval is conditional policy. Many effects are safely auto-executable within bounded authority.

## 10.3 Immutable static system Prompt — REJECTED

B02 and open-source prompt renderers show dynamic compilation from model/tools/mode/context/state.

## 10.4 Universal JSON function calling — REJECTED

CodeAct, XML/text protocols, provider-native mechanisms and streamed action formats are counterexamples.

## 10.5 Persistent memory as mandatory core — NOT SUPPORTED

B01 treats persistent memory as low-universality/product-specific. B02 shows multiple radically different context/memory strategies.

## 10.6 Plan/Todo as mandatory core — NOT SUPPORTED

Useful control state in many systems, but B01 classifies plan/task as an extension rather than the minimal Tool waist.

## 10.7 Subagents / multi-agent topology as mandatory core — NOT SUPPORTED

A01 shows sophisticated delegation, but B01 places subagents in the extension layer and the broader corpus does not make them necessary for a valid Agent loop.

## 10.8 Browser/Web as mandatory core — REJECTED

Important for some autonomous/app-building products but not needed for repository-local Agents.

## 10.9 Git/VCS as universal Agent primitive — REJECTED

It is extremely important in software engineering products, but belongs to that domain/product family rather than Agent architecture generally.

## 10.10 Universal global Agent state schema — REJECTED

The commonality is explicit state separation and projection, not one shared ontology.

```text
├─ context compilation
├─ model decision
├─ typed action surface
├─ authority/effect gate
├─ execution substrate
├─ explicit state projection
└─ verification/feedback loop

PRODUCT / DOMAIN SHELL
├─ repository + LSP + Git
├─ browser + desktop
├─ app preview/design system
├─ database/deployment
├─ communications/SaaS
├─ team topology
├─ persistent memory style
├─ checkpoints/version UX
└─ publication/release UX
```

This is more stable than organizing Agents by their Prompt text.

# 14. Final synthesis

Within the studied software-Agent/app-builder family, the most defensible shared architecture is:

> **An Agent product compiles a task-specific model view from scoped context and capability state, lets the model propose bounded actions through a Tool/effect surface, applies authority outside the Prompt, executes those actions in a real substrate, feeds structured observations into explicit working state, and repeatedly verifies/repairs until a bounded completion or publication condition is reached.**

Compressed:

```text
CONTEXT
   ↓
DECIDE
   ↓
PROPOSE ACTION
   ↓
AUTHORIZE
   ↓
EXECUTE
   ↓
OBSERVE
   ↓
UPDATE STATE
   ↓
VERIFY
   └──────────→ repeat / complete
```

The key result is therefore **not a universal Prompt, universal Tool list, universal DAG or universal multi-agent framework**.

It is a small set of recurring boundaries between cognition, action, authority, execution, state and verification.
