# Student Beachhead Discovery Experiments R1

Date: 2026-09-20
Status: PRE-INTERVIEW / NO MARKET VALIDATION YET

## 0. Purpose

Convert the hypotheses in STUDENT_MARKET_PRIMITIVE_CENSUS_R1 into external evidence with minimum infrastructure.

Do not deploy a CRM, student platform, education ontology or product first.

## 1. Research questions

1. Which student workflow causes enough repeated cost/risk/delay that the user actively seeks help?
2. Who experiences the pain, who approves use, and who can pay?
3. What is the current workaround and actual spend/time cost?
4. Which outcome is observable and valuable?
5. Which parts are already adequately solved by ChatGPT/Gemini/Copilot/Elicit/Consensus/Scite/LinkedIn/etc.?
6. What repeated residue remains after those mature tools are used?
7. Which information can legally/ethically be processed, retained and learned from?
8. Can Ordivon deliver a bounded outcome without performing prohibited assessed work?

## 2. First interview cells

Recruit separately; do not blend responses across materially different populations.

### Cell A — research-active technical students
Target evidence:
- currently doing a concrete paper/thesis/empirical project;
- has code/data/literature/analysis artifacts;
- can describe where the project repeatedly stalls;
- advisor/lab authority and payment route where relevant.

### Cell B — capstone/project/competition students
Target evidence:
- real repository or engineering artifact exists;
- team has milestone/demo/evaluation;
- inspect failure/rework/verification/reporting burden;
- record explicit course/competition AI policy.

### Cell C — technical students actively applying for internships/jobs
Target evidence:
- real target roles and applications;
- existing project/research evidence;
- current application process and outcome tracking;
- what career tools already solve versus what remains.

### Cell D — student founders / indie builders
Target evidence:
- real target customer or current product;
- current discovery/outreach/pilot activity;
- concrete blocker between building and getting paid.

Initial aim: enough interviews in each cell to discover repeated patterns, not to hit a ceremonial sample count. Continue while new material patterns are appearing; stop/narrow a cell when responses are repetitious or the hypothesis is clearly falsified.

## 3. Interview guide

Do not pitch Ordivon during the problem-discovery portion.

Ask for a recent concrete instance:

1. "Tell me about the last time you tried to do this."
2. "What triggered it?"
3. "What did you actually do, step by step?"
4. "Where did you get stuck or redo work?"
5. "What tools/people did you use?"
6. "What did it cost in time/money/opportunity?"
7. "What happened if you did it badly or late?"
8. "How did you know the result was good enough?"
9. "Who else had to approve/accept it?"
10. "What AI/tool policy constrained you?"
11. "What have you paid for already?"
12. "What would make you switch from the current method?"
13. "What part would you never trust an automated system to do?"
14. "What outcome would make a pilot obviously successful?"

Then, and only then, show one narrow offer hypothesis and ask for commitment-quality evidence:
- would they provide a real case?
- introduce the payer/authority?
- book a pilot?
- pay a small amount?
- sign up for a later pilot?
- allow follow-up after the real outcome?

Praise and feature requests do not count as strong evidence.

## 4. Evidence capture

For each interview retain only what is needed:

```text
participant segment
workflow instance
trigger
steps
pain/rework
current tools
current spend/time
authority/payer
acceptance/outcome
policy/rights constraints
exact notable evidence
offer reaction
commitment level
follow-up
```

Avoid unnecessary identity/sensitive data. Separate research notes from marketing/outreach consent.

## 5. First offer hypotheses

These are conversation probes, not products.

### Offer A — Research Reproducibility Pass
Input:
- existing research repo/data/method description.

Deliverable:
- reproducible execution map;
- environment/dependency evidence;
- rerun result;
- data/analysis integrity checks within declared scope;
- figure/table regeneration;
- explicit unresolved blockers;
- short advisor-ready evidence report.

Excludes:
- fabricating data/results;
- ghostwriting findings;
- claiming methodological validity outside the tested scope.

Success evidence:
- independent rerun;
- advisor/project-owner acceptance;
- reduced rework / resolved reproducibility blocker.

### Offer B — Technical Project Evidence Pass
Input:
- real project repo + requirements/demo rubric where permitted.

Deliverable:
- requirement-to-evidence map;
- build/test/security/dependency evidence;
- reproducible demo/release package;
- unresolved blocker list;
- portfolio-grade factual project evidence.

Excludes:
- completing prohibited assessed work for the student.

Success evidence:
- working artifact;
- passing relevant tests;
- evaluator/team acceptance;
- student can explain/defend the work.

### Offer C — Evidence-backed Career Portfolio Pass
Input:
- projects/research repos/artifacts + target role.

Deliverable:
- verified experience/skills inventory;
- claim-to-evidence links;
- gap map against selected roles;
- portfolio/resume factual rewrite;
- application outcome tracker.

Excludes:
- invented experience/skills;
- automated mass applications without explicit authorization.

Success evidence:
- recruiter response/interview progression over time;
- clearer verified portfolio;
- no unsupported claims.

### Offer D — Student Founder Validation Sprint
Input:
- specific product/problem hypothesis.

Deliverable:
- bounded market/customer research;
- competitor/substitute map;
- interview/outreach materials;
- evidence ledger;
- first offer/pilot draft;
- explicit kill/pivot conditions.

Success evidence:
- qualified customer conversations;
- pilot/paid commitment or clear falsification.

## 6. Decision rule after discovery

Do not choose a beachhead because interviewees "like" it.

A candidate advances when multiple real cases show:
- recurring painful workflow;
- reachable user and payer/authority;
- existing time/money expenditure;
- measurable acceptance/outcome;
- mature point tools leave a repeated unsolved residue;
- Ordivon can deliver that residue economically;
- rights/policy allow legitimate operation and learning.

The first paid pilot is the next major evidence threshold.
