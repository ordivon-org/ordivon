## 0. Purpose and authority boundary

This document replaces the old assumption that the ten campaign lanes define the Game capability ontology.

```text
AgentCount != E2ECount
LaneAssignment != DomainBoundary
OneLaneMayContainManyE2Es
OneE2EMayRequireManyAgents
```

Veilwild remains a non-canonical capability-pressure experiment. It does not select the first Ordivon Game product and does not enter canonical G0–G8 authority.

The purpose here is narrower and operational:

> Freeze the complete E2E subgraph that Project Veilwild R1 actually activates, then derive multi-agent execution topology from that graph rather than from an arbitrary fixed population.

## 1. Activation classes

Every candidate E2E is assigned one of four R1 classes.

### `CONSTITUTIVE`

Removing this closure would materially damage the current player thesis, intended loop, integrated acceptance, or one of T1–T7.

### `CLOSURE_CRITICAL_SUPPORT`

The capability does not define the player fantasy by itself, but without it Veilwild cannot produce a trustworthy integrated artifact, evidence condition, build, or standing.

### `PRESSURE_TRIGGERED`

Known capability family that should remain dormant unless an observed constitutive blocker demonstrates that the currently active carriers/processes cannot close the product requirement.

### `DORMANT_R1`

Explicitly outside the first R1 product scope. Its existence in the complete Game domain graph is preserved, but R1 must not activate it merely to appear comprehensive.

## 2. Veilwild R1 product closure

The experiment closes around one bounded player consequence:

```text
enter authored forest habitat
→ orient / learn observation interaction
→ read traces and multimodal cues
→ infer creature location/state
→ detect camouflaged Veilrunner
→ approach without sustained threat escalation
→ maintain intentional close observation
→ receive explicit observation consequence
→ optionally replay under a different creature position/state
```

Therefore the minimum full Veilwild closure is not `asset -> engine -> build`. It is:

```text
Product semantics
→ research-informed production constraints
→ authored environment / creature / motion / surface / audio
→ systemic creature/world response
→ engine realization
→ player interaction / feedback
→ exact build and runtime condition
→ independent technical/product evaluation
→ Human-playtest-ready condition
→ actual Human consequence when a participant is available
→ capability/product standing update
```

These do not independently define the forest-observation fantasy, but they are necessary for credible closure.


### V-C5 — Build / Packaging / Reproducibility E2E

Closure:


### V-C6 — Verification / Automated Test E2E

Own deterministic mechanical assertions for state transitions, import contracts, shader compilation, build launch and other non-Human claims.

### V-C7 — Performance Engineering E2E

Own diagnosis/repair of CPU/GPU/frame-pacing/loading/memory bottlenecks under exact current conditions.

```text
→ frame-time/pacing evidence
```

Closure:

```text

→ exact fields/timestamps/condition identity
→ durable evidence
→ later Human/product attribution
```

### V-C10 — Accessibility E2E

The slice relies on both visual and auditory information. Accessibility must test barriers such as visual-only cue dependence, audio-only cue dependence, text readability, motion, input remapping/feasibility and feedback redundancy.

Accessibility is both an owned closure and a cross-cutting plane.

### V-C11 — Independent Product QA / Red-Team E2E

```text

→ independent fresh-run attack
→ visual/audio/behavior/softlock/performance falsifiers
→ defect attribution
→ replay
→ standing
```

Producer-local test success may not substitute for this owner.

### V-C12 — Rights / Provenance E2E

Closure:

```text
asset/source/tool contribution
→ creator/source/license identity
→ modifications
→ build inclusion
→ defensible distribution right
```

R1 can use internally authored/generated assets, but selected shipping candidates still need explicit provenance.

### V-C13 — Workstation / Toolchain E2E

External constituent owned outside Game. The frozen professional loadout is apparatus input; Game may reopen it only through a real constitutive blocker.

### V-C14 — Engineering E2E composition

Game composes existing Engineering capabilities for requirements, architecture, implementation, integration, test, build, maintainability and repair. Game does not create a duplicate generic Engineering ontology.

## 7. Cross-cutting planes active in Veilwild R1

These are not ordinary children in the E2E graph.

### P1 — Evidence / Judgment Plane

Every meaningful claim must bind to exact source/artifact/build/execution/Human condition and an appropriate oracle.

### P2 — Authority / Admission / Cross-Owner Boundary Plane

Veilwild experiment authority is separate from canonical Game G0–G8 authority. This plane also governs Game↔Studio/Research/Engineering/Workstation ownership, scope admission and standing promotion. A separate eighth authority plane would duplicate this semantics.

### P3 — Condition / Revision Plane

Evidence is qualified by at least:

```text
source revision
asset revision
engine/project revision
build identity
machine/GPU/driver/render condition
resolution/display condition
Human protocol/participant condition when applicable
```

### P4 — Provenance / Rights Plane

Crosses all asset/research/tool/build contributions.

### P5 — Performance / Resource Budget Plane

Crosses environment density, creature asset, shader/rendering, AI, audio, engine, build and evaluation.

### P6 — Accessibility Plane

Crosses cue design, UI, input, visual treatment, audio and Human evaluation.

### P7 — Security / Privacy Plane — bounded R1 scope

No accounts/networked gameplay/commerce are active. The plane remains minimal but becomes material if Human telemetry leaves the local test boundary or external services enter the product path.

## 12. Agent population should be derived, not fixed

A naive 27-Agent one-front-per-Agent mapping would still be wrong because:

- F07/F08 may share one creature specialist early, then split under deformation/motion pressure;
- F10/F11/F12 interact tightly but have distinct failure modes and may merit 2–3 agents;
- F13/F14 may share a systemic simulation specialist until navigation becomes independently hard;
- F15/F16 may begin together, then split if spatial-audio propagation becomes material;
- F17/F19/F20 are tightly coupled integration work but should not absorb F25 judge authority;
- F22/F23/F24 need shared player-evidence interfaces but different oracles.

Therefore exact campaign population must be selected from **independent work fronts + expected contention + judge separation**, not from E2E count.

## 14. Explicit dormant frontier

The governing rule is:

```text
CompleteGameDomainGraph
→ select product scope
→ activate constitutive subgraph
→ allocate Agents from actual work fronts
→ allow new E2Es/fronts to emerge under pressure
→ keep unrelated domains dormant
```

not:

```text
pick N Agents
→ invent N lanes
→ call those the Game E2Es
```
