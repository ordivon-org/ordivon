# Ordivon Game Capability Activation Experiment — Round 1

> **2026-09-07 current-source transposition:** this campaign is a non-canonical `experimental-product` / capability-pressure instance. It does **not** select the first Ordivon Game product, does not enter G0, and does not supersede `docs/authority.md`, `docs/DEVELOPMENT_MODEL.md`, or the current Pre-G0 direction-search standing. Its authority is limited to the Veilwild R1 experiment and the evidence it produces.


## 0. Experiment question

This round does **not** compare Game-driven capability development against isolated capability development.

It tests one narrower hypothesis:

> Can one demanding, integrated, high-quality Game production create real product pressure that activates previously dormant or near-absent Ordivon capabilities, causing those capabilities to become evidence-bearing production capabilities rather than merely available tools or topics?

Formally:

```text
Dormant / near-absent capability
→ authentic product demand
→ capability gap becomes blocking
→ mature external tool / standard / knowledge selected
→ first real production use
→ integrated Game artifact
→ independent evidence
→ scoped capability standing improves
```

The experiment is successful even if the Game does not activate every target capability. It fails if agents merely write capability reports, open tools, generate disconnected demos, or narrate apparatus availability as capability.

## 1. Product pressure source — Project Veilwild

Build a coherent **3D ecological stealth / observation vertical slice** of a larger game.

Working title:

```text
Project Veilwild
```

Player fantasy:

> Enter a living forest habitat, track a biomimetic creature, learn the subtle visual/motion/audio cues that reveal it, approach without startling it, and obtain a successful close observation while the creature uses camouflage/mimicry and adaptive behavior to remain hidden.

The slice should feel like one piece of a serious larger game, not a technology showcase.

### Intended player loop

```text
enter habitat
→ orient and learn basic observation interaction
→ encounter environmental/behavioral traces
→ infer creature location/state
→ detect a camouflaged/mimetic creature
→ approach / observe without triggering escape
→ receive a clear successful observation consequence
→ optionally replay and discover a different behavior/position
```

Target first-session duration: roughly 8–15 minutes, but do not pad runtime artificially.

No combat is required. Do not add multiplayer, UGC, live economy, LLM NPCs, voice acting or giant open-world systems merely to increase feature count.

## 2. Why this product was selected

The game thesis naturally creates non-optional demand for several weak or previously underused capability domains:

```text
3D asset production
rigging / animation
materials / lighting / camouflage
realtime VFX where useful
spatial audio
adaptive / state-responsive music or ambience
biomimetics / biological research transfer
creature behavior simulation
human visual/auditory perception
3D engine integration and performance
professional Workstation tool use
```

The test is not whether these tools are installed. The test is whether they carry real product responsibility.

## 4. Primary activation targets

These are **targets to pressure**, not mandatory success claims.

### T1 — 3D production

Desired transition:

```text
near-absent / weak real Game use
→ editable environment + creature assets
→ engine integration
→ real change/reimport loop
→ runtime evidence
```

### T2 — rigging / animation

Desired transition:

```text
little or no real production evidence
→ creature rig
→ locomotion / idle / concealment / reaction motion
→ runtime transition behavior
→ visual/gameplay validation
```

### T3 — material / camouflage / mimicry rendering

Desired transition:

```text
concept only
→ environmental visual model
→ realtime camouflage/mimicry implementation
→ lighting/material behavior
→ player-facing detectability consequence
```

### T4 — spatial / interactive audio

Desired transition:

```text
simple cue playback
→ positional/environmental audio
→ useful detection information
→ mix/priority/occlusion or attenuation behavior where justified
→ in-game validation
```

Adaptive music/ambience is useful only if it improves the product thesis; do not force a complex music system with no player consequence.

### T5 — biomimetics / biological research transfer

Desired transition:

```text
Research E2E knowledge production
→ current external biological/behavioral evidence
→ explicit abstraction into Game behavior/material/animation requirements
→ implemented behavior
→ product evidence
```

Scientific inspiration must not be marketed as biological simulation fidelity beyond the evidence.

### T6 — creature behavior / ecological simulation

Desired transition:

```text
simple scripted target
→ stateful/perceptive creature behavior
→ conceal / freeze / orient / evade or equivalent biologically motivated loop
→ environment-dependent response
→ reproducible/systemic evidence
```

A conventional state machine / behavior tree / utility policy is preferred unless richer cognition is genuinely required.

### T7 — perceptual / Human evidence readiness

Desired transition:

```text
machine-only game validation
→ instrumented player-facing detectability/comprehension claims
→ a real Human playtest protocol and evidence capture path
```

Agents may perform expert/mechanical checks. They may not claim actual Human fun, detectability, immersion or fairness until a real Human participant supplies that evidence.

## 6. Quality target

The final product must not collapse to another minimal HTML/JS proof.

Expected target is a **real 3D executable vertical slice**, preferably using current Godot 4.7.1 unless source-current evidence shows a materially better already-available engine path.

The final slice should aim for:

- coherent visual direction rather than unrelated generated assets;
- a real environment, not primitive cubes as final representation;
- at least one authored/generated-but-editable creature asset with meaningful shape/material identity;
- actual rig/animation or an equivalent real motion production path;
- camouflage/mimicry that matters to player detection rather than a decorative shader toggle;
- creature behavior that reacts to the environment/player;
- spatially meaningful audio;
- clear input, feedback and success/failure consequence;
- source-current build reproducibility;
- no obvious crash/softlock on the intended loop;
- measured technical performance on the actual current workstation/build condition;
- provenance/rights clarity for selected shipping assets;
- a Human-playtest-ready build and protocol.

Target technical ambition on the current RTX 5060 laptop is stable interactive performance around a 60 Hz experience at 1080p where the selected engine/render path reasonably supports it. Treat this as a product target to measure, not a universal pass threshold and not an excuse to lower visual quality without evidence.

## 8. Common execution law

All ten agents work on **one product**.

This is not ten independent essays or ten competing games.

Use Runtime/Host/current repositories for coordination and exact source truth.

Agents may create isolated workspaces/branches/commits and exchange exact commits/artifacts. The integration owner may cherry-pick/rebase/merge validated changes into an integration candidate. Do not directly modify canonical `main` unless separately authorized.

Every lane must:

1. inspect source-current Game state before work;
2. inspect existing owner/tool evidence instead of assuming capability absence/presence;
3. communicate decision-relevant interfaces early;
4. produce actual integrated artifacts/code where its responsibility requires them;
5. validate its own output;
6. provide exact handoff identity and known limitations;
7. avoid claiming Human or cross-domain capability beyond evidence.

## 9. Lane assignments

### Lane A — Product / Creative Direction / Integration Owner

Own coherence of the single playable slice.

Responsibilities:

- freeze the smallest coherent game thesis and player loop;
- decide scene/experience priorities;
- maintain integration head/candidate;
- prevent feature accumulation unrelated to the thesis;
- consume lane handoffs and resolve product-level conflicts;
- ensure the final game feels like one product rather than ten demos;
- maintain a short current integration/blocker view;
- produce final playable build candidate and exact source identity.

Do not redo specialist work merely to centralize ownership.

### Lane B — Biomimetics / Research-to-Product

Use the existing Research E2E to establish a bounded evidence base for camouflage/mimicry and creature behavior relevant to the selected creature.

Responsibilities:

- use current reputable biological/behavioral sources;
- distinguish biological fact, plausible inspiration and fictional design;
- translate evidence into implementable requirements for lanes D/E/F;
- avoid a literature-review-only outcome;
- validate that at least one research-derived behavior/visual principle reaches the actual build.

This lane is successful only if Research changes the product.

### Lane C — 3D Environment / Lighting / Material Production

Create the habitat production path.

Responsibilities:

- use Blender/current DCC tooling where appropriate;
- produce editable environment sources and runtime assets;
- establish a coherent art/lighting/material direction supporting concealment/detection;
- perform at least one real source-change → export/import/rebuild loop;
- coordinate performance needs with H and mimicry needs with E;
- preserve exact source/interchange/runtime distinctions and selected-asset provenance.

No final scene made only from engine primitives.

### Lane D — Creature 3D / Rig / Animation

Create the creature as a real animated product asset.

Responsibilities:

- editable creature source;
- rig/skeleton or equivalent controllable deformation system;
- locomotion + idle/concealment + threat/reaction behavior sufficient for the loop;
- runtime transitions;
- align visual motion with gameplay/AI state from F;
- eliminate obvious sliding/contact/state-transition defects where feasible;
- provide exact DCC/engine handoff evidence.

Opening Blender and exporting one static mesh is not activation.

### Lane E — Mimicry / Camouflage / Rendering / VFX

Make concealment a real game mechanic.

Responsibilities:

- turn B's research/product requirements into a render/material strategy;
- integrate with C environment/lighting and D creature asset;
- make camouflage depend meaningfully on environment/state rather than a simple invisibility toggle;
- preserve player-readable counter-cues so concealment can be learned rather than becoming arbitrary invisibility;
- use engine-native shader/VFX capability where it is the mature path;
- create mechanical/perceptual proxy tests without claiming Human detectability.

### Lane F — Creature Behavior / Simulation / Ecology

Implement the creature's behavior loop.

Responsibilities:

- perception/awareness of player/environment as required;
- conceal/freeze/orient/evade or equivalent stateful behavior;
- environment-dependent choices;
- deterministic/reproducible debug/evidence path where feasible;
- conventional behavior mechanisms first; no LLM Agent unless deletion pressure fails;
- coordinate animation state with D, camouflage state with E and cues with G;
- expose systemic failure cases instead of hiding them with scripting.

### Lane G — Spatial Audio / Music / Interactive Sound

Make audio carry real player information and atmosphere.

Responsibilities:

- create/select rights-safe editable audio sources;
- spatial creature/environment cues useful to tracking;
- attenuation/priority/occlusion or equivalent runtime behavior where product-relevant;
- coherent ambient mix;
- adaptive music/ambience only if it materially improves the game thesis;
- use REAPER/FFmpeg/current audio tooling where appropriate rather than inventing a DAW;
- validate runtime binding and listening/mechanical dimensions separately.

`AudioBindingPass != InteractiveAudioQuality`.

### Lane H — Engine / Engineering / Performance / Build

Own the technical realization path, not the game's creative meaning.

Responsibilities:

- engine/project structure and integration support;
- input/camera/player movement;
- runtime/game-state plumbing required by specialist lanes;
- build/reproducibility;
- performance profiling under an exact execution condition;
- frame pacing/hitches/memory/loading where material;
- clean launch and loop completion;
- exact tested artifact identity.

Prefer current Godot 4.7.1 unless a better already-supported path is justified. Do not spend the round writing a custom engine.

### Lane I — UX / Accessibility / Player Evidence Instrumentation

Make the product understandable and Human-evidence ready.

Responsibilities:

- controls / interaction feedback / observation success state;
- onboarding without destroying the discovery fantasy;
- accessibility barriers relevant to this slice, especially visual-only/audio-only cue dependence, text/UI, motion and input;
- instrument useful player-facing events such as time-to-first-cue, first detection, false detections, creature startle/escape and successful observation where feasible;
- prepare the exact real-Human playtest protocol for the user/participants;
- perform mechanical/expert checks without laundering them into Human claims.

### Lane J — Independent Red Team / Product QA / Activation Auditor

Remain meaningfully independent from producers.

Responsibilities:

- repeatedly test source-current integration candidates;
- reject false-green lane claims;
- verify the complete loop from fresh launch;
- inspect visual/audio/behavior coherence, not only unit tests;
- pressure softlocks, impossible detection, trivial detection, state desynchronization, missing assets, bad transitions and performance hitches;
- verify exact artifact/source condition;
- audit dormant-capability activation claims against actual integrated evidence;
- make targeted repair commits only when a severe defect would otherwise remain and independence can still be documented.

J is not a report-only lane.

## 10. Cross-lane interfaces that must converge

These are product interfaces, not permanent schemas.

### Creature state

D/E/F/G must agree on the active product semantics for states such as:

```text
unaware / idle
alert / orient
conceal / mimic
flee / evade
observation-success consequence
```

Names may change. Meaning must not drift independently across animation, shader, AI and audio.

### Environment affordance

C/E/F must agree on what environmental features make concealment possible and how those features are represented at runtime.

### Player evidence

E/F/G/I must agree on what cues are intentionally available to the player and which claims remain Human-unknown.

### Performance

C/D/E/F/G/H must treat GPU/CPU/audio/content load as one integrated runtime budget, not separate local successes.

## 11. Final integrated acceptance

The coordinator/red team should classify the final result rather than force PASS.

A strong result requires at least:

### Product

- fresh launch reaches the intended 3D scene;
- player can understand basic interaction;
- one complete tracking/detection/approach/observation loop is reachable;
- creature visual, animation, behavior, camouflage and audio are integrated into the same product condition;
- there is a clear success consequence;
- no critical path depends on missing external manual editing after build creation.

### Technical

- exact source revision and tested artifact known;
- build/run path reproduced;
- no obvious crash/softlock in independent run;
- performance measured under declared current condition;
- selected assets have defensible origin/rights standing;
- no test result is transported across materially different build conditions without justification.

### Capability activation

At least several target domains must show evidence like:

```text
APPARATUS_ONLY / NOT_OBSERVED
→ actual product demand
→ integrated artifact
→ independent evidence
→ SUPPORTED_WITHIN_SCOPE
```

It is acceptable for some targets to remain `INCONCLUSIVE` or `NOT_OBSERVED`; report that rather than manufacturing success.

### Human boundary

The agents may deliver a Human-playtest-ready build and protocol.

They may not claim:

```text
fun
immersion
believability
Human detectability
Human fairness
```

as established until actual Human evidence exists.

## 12. Final campaign outputs

Produce one integrated product candidate plus compact evidence, not ten disconnected portfolios.

Expected outputs:

```text
1. playable 3D build / exact run instructions
2. exact integration source revision
3. editable selected source assets/projects needed for future revision
4. mechanical / technical verification receipts
5. Game/Product standing summary
6. Capability Activation Matrix — before vs after
7. unexpected capability activations
8. failed / still-dormant capabilities
9. exact blockers and next highest-value pressure
10. Human playtest protocol and current Human-unknown claims
```

## 13. Campaign success question

At closeout, answer this—not “did ten agents work?” and not merely “is the game good?”

> Did one authentic, coherent Game product requirement cause previously dormant or apparatus-only capabilities to become real evidence-bearing production capabilities, and can we point to the exact integrated product consequence that forced and validated each activation?

If yes, the capability-activation effect survives Round 1.

If the final result is merely a bundle of demos/reports/tool invocations, it does not.
