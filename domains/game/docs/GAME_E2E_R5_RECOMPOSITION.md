# Game E2E R5 — Domain Kernel / Subtraction / Recomposition

## 0. Why this round exists

R1–R4 proved that Ordivon Game can build, integrate, falsify and bind exact playable evidence, but the production experiment also accumulated Game-local copies of generic Host/workflow, build, provenance, testing, telemetry and recovery machinery.

R5 is a subtraction/recomposition round. It does **not** continue Veilwild feature production and does not create a general game platform.

The target is:

```text
Game E2E
= Game-owned semantic kernel
+ thin game/profile projections
+ products / apparatus / regression corpus
+ thin adapters to owner-external E2Es and mature substrates
```

not:

```text
Game E2E
= research + workflow + build + artifact + telemetry + release + operations reimplemented locally
```

Game retains semantic authority already frozen by the current foundation programme:

- GDF0 — Play / Game;

## 5. R5 hard invariants

The following R1–R4 findings survive subtraction:

1. **Exact candidate identity** — evidence must resolve to the exact evaluated candidate/build/condition.
2. **No green inheritance** — changed source/artifact/evaluation condition/player context does not inherit PASS by default.
3. **Impact-aware invalidation** — unchanged evidence may survive only through explicit dependency/impact reasoning.
4. **Same-candidate composition** — independent evidence from different candidates must not be silently composed into one PASS.
5. **Owner semantics** — telemetry, consumers and observers do not mint Game meanings owned elsewhere.
6. **Technical != Human** — technical correctness never upgrades fun, fairness, comprehension, immersion, comfort or accessibility fit.
7. **Human UNKNOWN is legitimate** — Human/player claims remain UNKNOWN until admissible player evidence exists.
8. **Rights fail closed** — provenance evidence alone does not imply distribution rights.
9. **Response loss != non-occurrence** — uncertain durable effects are observed/recovered by original identity, not blindly resent.
10. **Independent destruction** — maturity promotion requires independent adversarial replay, not producer self-certification.
11. **Non-spoiling observation** — telemetry/projections must not expose hidden game truth merely because the runtime owns it.
12. **Historical evidence stays historical** — old negative/UNKNOWN evidence is preserved and never rewritten to match a newer architecture.

## 6. Player evidence bridge

Game player research is an explicit Research E2E consumer.

A material player question projects as:

```text
researchIntent   = the decision blocked by player uncertainty
targetOfInquiry  = exact game/build/condition/player population/session context
claimBoundary    = what Human/game claim may and may not be generalized
evaluationLogic  = the method-appropriate decision rule
```

Examples of Game-owned questions:

- can players distinguish concealment from target disappearance?
- is reacquisition perceived as fair?
- which cue is actually used to recover the target?
- does the intended learning survive delayed transfer?

Research selects the valid method. Engineering supplies the exact instrumented candidate. Artifact binds build identity. Operations may transport observations. Game adjudicates the player-relevant meaning within the scoped claim.

## 7. Candidate model

R5 does not introduce a Game candidate database.

A Game evaluation requires a thin immutable evaluation reference capable of resolving, through Artifact/Engineering owners, at least:

```text

build/toolchain/configuration
target platform
build artifact
evaluation condition
player/context boundary when applicable
```

Hashes, attestations, SBOMs and supply-chain receipts remain Artifact/mature-substrate concerns.

## 8. Accessibility

Accessibility is not a late single gate.

```text
Game           → player-facing requirement / intended alternative channel
Engineering    → implementation and technical validation
Research       → relevant-player usability/accessibility evidence
Artifact       → exact candidate identity
Distribution   → target-channel requirements
```

A checklist or technical alternative cue does not by itself prove population-specific accessibility fit.

## 9. Telemetry

Game owns event meaning; Operations/OpenTelemetry-class infrastructure owns transport/observation mechanics.

```text
Game domain event
→ transport / trace / metric / log
→ analysis
```

never:

```text
raw movement/state data
→ telemetry layer invents "reacquisition" or other Game-owned semantics
```

## 10. Rights / provenance / distribution

```text
Artifact E2E      → artifact/source lineage and provenance
Rights source     → license/ownership/attribution facts
Distribution E2E  → channel-specific release requirements and actions
Game E2E          → game-relative admission under the intended use/distribution claim
```

`provenance valid` is not equivalent to `distribution authorized`.

## 11. Migration order

R5 proceeds only in this order:

1. freeze exact current source and R1–R4 counterexamples;
2. classify Game modules by semantic owner;
3. define lossless substitution targets;
4. add thin owner adapters where a current consumer exists;
5. replay Station Zero and Veilwild failure matrices;
6. delete duplicate generic machinery only after substitution + replay proof;
7. run independent destroyer review;
8. promote default-ready only if cross-game judgment power is preserved while Game-owned generic machinery is measurably reduced.

## 12. Explicit non-goals

## 16. R5 migration milestone M4 — Workstation professional-software binding

R5 found that Workstation already owns a `professional_software` census for installed tools, while the shared `equipment-binding` interface previously exposed only isolated, managed-external and browser-specific carriers. An engine consumer therefore had no lossless generic binding for a stable package-managed engine.

A detached source-current Workstation candidate from `55302746d619430c1326d54ed94bd275a9baea04` is frozen as:

```text
66ed480b7a66308bd1667878c0f55a68dfc9c2bf
```

It adds:

```text
equipment-binding professional
  --software-id <declared professional_software identity>
  --launcher <declared launcher name>
```

The caller cannot provide an executable path. Workstation resolves the configured launcher, verifies the Linux executable and binds its SHA-256. Windows professional-software entries deliberately fail closed in this Linux projection rather than receiving inferred Windows-native truth.

For current Godot the candidate resolves:

```text

provider          = workstation.professional-software

executableDigest  = sha256:a72fa47eb84dab812102e622f3fa9e99754505459a0ded8f69ceddd5b4ded8dd
```

Game now exposes `engine.project.execute` as a domain operation that requests only `software-id=godot` and `launcher=godot`. Game does not store `/usr/bin/godot`, discover PATH, install Godot, infer its version, or gain physical-binding authority.
