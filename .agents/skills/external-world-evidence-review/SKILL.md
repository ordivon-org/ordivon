# External-world evidence review

## When to use
Activate for an external world event, public institutional decision, primary empirical result, published standard, failure or genuine counterexample when a **specific** existing question, model, risk assumption, policy or capability-consumer decision might change. For ordinary newspaper summarization with no identified consumer, use the current daily-world-brief method instead. Do not require a fictitious consumer just to keep a record.

## Natural responsibilities
- External issuer/standard/provider: occurrence, content, edition and primary measurement (under that issuer's actual authority).
- Research / relevant domain Owner: hypothesis, causal interpretation, evidence sufficiency, decision to revise and resulting domain acceptance.
- Catalogs/Knowledge: task-relevant external methods and provenance mappings only; not a fact database.
- Skills: procedure discovery and advice, never permission or source truth.
- Composition: existing task-local gates and, when needed, successor comparison; never automatic domain acceptance.
- Runtime: physical Jobs/Artifacts, not research or market truth.
- Host: Work/Space/Topic/Message continuity, not automatic evidence-store truth.
- World: exact external-effect and provenance boundary only when a real external-World interaction requires it.

## Five evidence steps
1. **Bind one falsifiable question.** Name the concrete prior claim, its period, unit and frozen source/model identity when available. Missing baseline or consumer is UNKNOWN, not an invitation to invent one.
2. **Read the origin.** Use an issuer primary document, native data source, original paper or provider-native inspection. Record issuer identity, direct support scope and separate eventAt, reportedAt, dataAsOf, revisedAt (only when known) and checkedAt. Never substitute article indexing time for report time. Record contradictory evidence and independent witnesses when the claim is consequential.
3. **Express only a supported delta.** Match subject, instrument, population, units, denominator and periods. Use native Decimal/arithmetic, accepted statistics or domain validators rather than writing an Ordivon-specific delta engine. A state transition is not a number; an issued policy is not an implemented effect. Source-only claims remain attributed.
4. **Route to real consumer.** Read the natural Owner's existing hypothesis/policy/code and its actual consumers. Record exactly which assumption is challenged; absence of an identified consumer is a lawful no-op. For causal claims, compare rival explanations, identify discriminating tests, and use Research's existing methods.
5. **Validate and close the loop.** Only the domain Owner may revise its own model or practice. Bind original version, new version, evaluation anchor, independent evidence and post-change readback. A Composition gate PASS or Runtime exit zero does not imply domain acceptance. If no validated benefit or evidence is sufficient, KEEP / HOLD / UNKNOWN, with a concrete falsifier.

## Choose standards by job, not by decorating a schema
Resolve the **existing Authority Catalog** for the exact specification before applying it. For the following three registered standards use the catalog's native CLI `python3 catalogs/authorities/scripts/authority_catalog.py show <id>` and check the `latestObservation` as well as the issuing source. A catalog record is discovery/currentness evidence, **not** a domain acceptance or proof that any upstream claim is true.

- `w3c-prov-o-2013`: W3C PROV-O (https://www.w3.org/TR/prov-o/) only for actual Entity/Activity/Agent provenance and derived relations. Do not construct a universal PROV graph for one headline.
- `cloudevents-1.0.2`: pinned CloudEvents 1.0.2 (https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md) only for actual event exchange. `source`+`id` duplicate identity and RFC3339 `time` are transport semantics, **not** independent proof a claim occurred.
- `openlineage-spec`: the official OpenLineage specification as identified by the current Authority Catalog observation. Use it only for actual run/job/dataset lineage consumers, not for a generic collection of source URLs; versioned facet schemas and documentation-version labels must not be conflated with the specification's normative edition.
- Existing Research qualification and method-router Skills when experimental evidence or theory selection is needed; existing Security/Skill supply-chain procedure for untrusted external executable instructions.
- Existing external-capability-evaluation Skill, **only when discoverable**, for software/algorithm candidates. An external repository is a capability candidate, **not** automatically a formal LEGO.

## Finished work reports
For humans: identify changed fact, date, credible source, earlier baseline, supported delta, affected real decision, verdict and next observable falsifier in ordinary Chinese prose. For agents: retain source/version/authority references, exact consumer binding, verifier scope and status separately; only persist to the natural Owner where it already has an admitted write/read-back contract.

No automatic market order, software installation, deletion, release or promotion follows from discovering a source. Do not create a central Event/Knowledge/LEGO Registry, scheduler, universal status ontology or private replacement for mature standard capabilities. Do not retain dated sample packets or one-off normalization scripts merely because they have self-referential CI tests.
