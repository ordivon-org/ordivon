# Ordivon Runtime Model

## Purpose

A participant, Agent, or Host forms and admits work. Ordivon Runtime executes it, owns the resulting process tree, records non-reconstructable execution truth, and reconciles that truth after interruption.

## Boundaries

Runtime owns physical operation admission, process-tree supervision, durable execution identity, bounded result evidence, cancellation, reconciliation, and Workspace lifecycle. Git, SQLite, systemd/cgroups, digest-bound files, and generated MCP schemas remain the strongest owners of their respective facts. Host and participants retain semantic completion, purpose, and commitment judgments.

### Component responsibility matrix

| Component | Owns | Explicitly does not own |
| --- | --- | --- |
| Runtime | Workspace lifecycle, physical operation admission, Jobs, Attempts, process trees, bounded Artifacts, cancellation, reconciliation, and enforceable effect receipts | Task/Goal semantics, Assignment or Run policy, Provider execution, domain verification, or product policy |
| Host | durable Task continuity, Journal/CAS, generic extension admission, commitment identities, verification records, and Task outcomes | Harness-specific Run schemas, Provider loops, physical execution truth, or domain-world truth |
| Harness | Task Attempt and Assignment semantics, Agent Runs, Provider adapters, model–Tool loops, Tool-step checkpoints, Run recovery, and completion proposals | generic Task persistence, another database or scheduler, Runtime supervision, promoted protocol, or final domain authority |

## Data flow

```text
request
→ exact Git Workspace
→ transactional admission
→ Job + Attempt + reservation
→ immutable runner bundle
→ systemd transient unit and cgroup
→ bounded result and Artifacts
→ reconciliation
```

A Workspace isolates the checked-out code tree and Git state. It does not reduce the installed service user's host authority.

## Truth owners

| Fact | Owner |
| --- | --- |
| Repository history, diff, rollback, Workspace identity | Git |
| Request identity, Job, Attempt, reservation, cancellation, resolution | SQLite Registry |
| Running process tree and termination | systemd and cgroup |
| Result and Artifact bytes | Digest-bound files |
| Public Tool contract | MCP schema generated by the server |
| Current deployment and health | live service, configuration, Git, and Runtime inspection |

Information reconstructable from these owners should not be persisted as a second proof system.

## Components

```text
Principal
└── submits an idempotent request
    └── identifies one Job in one Workspace
        └── owns an Attempt
            ├── consumes a concurrency reservation
            ├── binds an immutable runner bundle
            ├── owns one systemd unit and process tree
            └── produces a terminal Result and Artifacts
```

The Job expresses desired state and final resolution. The Attempt expresses one bounded execution history. Conditions and append-only events preserve the evidence needed to understand incomplete or corrected state without inventing another execution path.

## Irreducible invariants

- Repeating the same authenticated client request is idempotent.
- A candidate Agent action is not physical commitment until durably admitted.
- One Attempt crosses the physical dispatch boundary at most once.
- An ambiguous dispatch is never speculatively repeated.
- Durable admission and physical dispatch are separate boundaries: Runtime may serialize Workspace/admission decisions briefly, but a Registry reservation—not the lifecycle mutex—owns capacity, and a newly admitted Job is physically dispatched only after the Workspace lifecycle lock is released.
- A newly admitted Job binds the exact Runtime-owned execution provider contract and executable digest; provider drift before dispatch fails closed instead of changing the machinery that realizes an already committed operation.
- One Attempt owns the complete command process tree through one cgroup.
- After that process tree is proven gone, a complete identity-bound Runner Result is terminal execution truth.
- Execution truth is not automatically an external-effect receipt or semantic-completion proof.
- Work that cannot be proven running or terminal becomes `lost` or `orphaned`; it is not guessed successful, guessed failed, or automatically redispatched.

The complete Agent Effect Commit Kernel contract, current proof boundary, costs, and implementation gate are in [`effect-kernel.md`](effect-kernel.md). Other exact limits, states, fields, transitions, Tool arguments, and configuration belong to source, migrations, tests, generated schemas, and the live Runtime.

## Failure modes

Runtime preserves ambiguous dispatch, missing terminal evidence, residual process ownership, stale source commitment, capacity exhaustion, and cancellation races as explicit failure or recovery states. It must not guess success, hide uncertainty, or redispatch an opaque operation merely because a response was lost.

## Reconciliation

Reconciliation compares Registry state with runner evidence and systemd/cgroup reality. It runs during startup recovery, configured background maintenance, execution admission for the relevant Workspace, explicit maintenance calls, and exact-Job `job.observe`. Projection-only listing/get paths do not reconcile or dispatch work. One Job's recoverable inconsistency must not expand into a service-wide failure.

## Terminal supervision evidence

Every terminal Attempt registers `terminal-evidence-<digest>.json` as a `terminal_evidence` Artifact. The evidence binds the durable Job and Attempt to the committed Workspace, source revision, execution profile, optional foreign references, explicit Host Dependency prerequisite commitments when present, exact command, systemd unit, invocation, cgroup, PID identity, Runner-start digest, terminal reason, and the other terminal Artifact identities. It projects three orthogonal facts instead of expanding the Job state machine:

- `executionDisposition`: the committed Attempt terminal state;
- `deliveryDisposition`: whether the terminal result was committed, is unknown, or still requires reconciliation;
- `processTreeDisposition`: `terminal_clean`, `unexpected_residual`, or `unknown`.

Runtime prefers the recursive cgroup-v2 `cgroup.events: populated` fact and falls back to direct `cgroup.procs` membership only when the events file is unavailable. The evidence remains an Artifact consumed through `job.observe` and `artifact.read`; Runtime does not add a parallel evidence Tool or foreign-reference database. Foreign references are immutable opaque inputs in the Execution Plan and therefore participate in request identity, replay conflict detection, and the plan digest; Runtime does not impose an arbitrary count ceiling on them.

### Host correlation convention

Harness-originated execution uses opaque `ordivon.host` foreign references for the Host Task, Host Task Attempt, Assignment, and Harness Run. The Host places Task revision in the `task` generation, Assignment generation in the `assignment` generation, and binds each reference to its Host-owned digest. Runtime preserves these values exactly; it does not interpret Assignment validity, Harness capability, or Host Task state.

Exact `clientRequestId` replay with the same execution request and references returns the original Runtime Job. Changing Assignment generation or digest under that request identity is an idempotency conflict, so stale work cannot masquerade as replay. A recovery caller locates the original Job with the exact `clientRequestId` and reads its immutable Execution Plan or terminal-evidence Artifact. Runtime success remains physical execution evidence; semantic CompletionProposal adjudication and TaskOutcome commitment remain Host-owned.

The public `job.get`, `job.observe`, `job.list`, and `job.cancel` names remain ordinary Runtime Job Tools rather than MCP Tasks extension methods. `job.get` and `job.list` are projection-only reads; `job.observe` may reconcile or dispatch the exact already-admitted Job; `job.cancel` persists stop intent and reconciles the owned process tree. Public prose distinguishes Host Task Attempt, Harness Run, Runtime Job, and Runtime Attempt; Runtime adds no Host-specific enum, state table, query service, or semantic-completion authority. Agent-facing Job projections expose `semanticCompletionEvaluated=false` only as an explicit negative boundary so execution success cannot be mistaken for Task or domain completion.

A verified terminal result can defeat a later cancellation race because observed completion is stronger evidence than delayed intent. An identity-uncertain Attempt remains `orphaned` and retains its reservation while its recorded unit, process identity, or cgroup may still own a live process tree. When all three are proven absent, reconciliation converges it to `lost`, `timed_out`, or `cancelled` according to persisted intent and releases the reservation atomically. A late identity-bound runner Result still takes precedence when available.

Control-side terminalization has one additional serialization boundary that is deliberately narrower than process stopping. Cancel and generic supervisor reconciliation may observe the same vanished process tree concurrently and both need the shared control-result/evidence path. Runtime serializes only the short sequence that re-reads the current Attempt, writes control result/evidence, and commits the terminal Registry CAS; it does not hold that lock while waiting for systemd stop. Persisted termination intent selects the generic missing-unit outcome when the recorded process is also gone: `stop_requested` produces the cancellation terminal identity and reason, deadline intent produces timeout, and natural disappearance keeps the generic lost/failure classification. Runner-owned `result.json` remains a separate exact terminal claimant and can still win according to Registry terminal identity law.

## Workspace source commitment

A `clientRequestId` binds the stable operation request separately from the observed Workspace. Replaying the same request returns the original durable Job without resolving the current Workspace again, including after that Workspace has changed or closed. The initial admission then binds a digest of the Workspace's Git source state: current `HEAD`, the semantic Git index including index flags, every tracked path's actual file or symlink bytes and mode, recursively initialized submodule source state, and sorted nonignored untracked files or symlinks. Ignored caches and build outputs are deliberately excluded. The digest participates in operation identity and is checked again by the Runner immediately before the target executable is spawned.

The Runtime rejects `workspace.mutate` while an active or held Job owns that Workspace. This prevents Runtime-mediated mutations from changing the committed source world during execution. `workspace.mutate` is an atomic digest-guarded synchronous convenience and intentionally has no second durable request ledger. When mutation itself needs response-loss-safe replay/recovery, use `workspace.exec` with the selected mature mutation tool so the existing Job/Attempt ledger remains the sole durable execution lifecycle. Editing and execution that must overlap use separate Workspaces rather than weakening one Job's source precondition. `workspace.diff` independently projects Git path status into sorted changed, modified, added, deleted, renamed, and untracked sets while retaining bounded diff text.

This is a trusted-local pre-spawn commitment, not an immutable filesystem snapshot. A host process with the same authority can still write directly outside the Runtime, including in the interval after Runner validation, and a running command may intentionally modify its own Workspace. Ignored files, wall-clock time, network state, and other ambient dependencies are not included. Target processes do not inherit the Runtime service environment: the Runtime binds configured `ORDIVON_EXEC_PATH` and `ORDIVON_EXEC_HOME` values plus a fixed locale, temporary directory, and explicit cache paths into the committed execution plan, then overlays only the request's explicit environment. For `trusted_local`, `TMPDIR` is a fixed-length `/tmp/ordivon-t/<20hex>` presentation symlink derived from the canonical physical Runtime store namespace plus Workspace identity whose bytes still live in the Workspace-owned `cache/tmp/<workspaceId>/` backing; this keeps descendant Unix-socket path length independent of Runtime store and Workspace-ID depth while preserving Workspace cleanup ownership. `contained_local` keeps the direct backing path. In `trusted_local`, package-download caches are global to the Runtime while each Workspace still owns a distinct physical Cargo target backing under `cache/build/<workspaceId>/cargo`. The Runner presents that private backing to the target through one stable inherited directory descriptor at `CARGO_TARGET_DIR=/proc/self/fd/198`. Two concurrent Jobs can therefore observe the same compiler-visible target pathname while writes remain in different Workspace-private backings. This presentation was adopted only after physical sccache experiments showed that changing otherwise-private Cargo target pathnames destroyed cross-Workspace compiler-cache reuse; it does not share target bytes, install a cache daemon, or make compiler cache contents Runtime truth. Because the Workspace build target is excluded from source-state commitment and recreated by ordinary execution-environment construction, an open-but-idle Workspace may lose that reconstructible target under retention pressure, but only through an admission-fenced eviction whose durable plan binds the observed Registry Job/Attempt activity identity. Inside the fence Runtime rechecks active/held ownership, Workspace-record standing, and that exact activity marker before atomically detaching the tree from its execution pathname; even a Job that was admitted and completed while prune waited invalidates the stale plan for that round. This is cache eviction, not Workspace semantic disposition, and it does not depend on an arbitrary age threshold; generic and temporary Workspace cache paths retain their more conservative open-Workspace protection. `contained_local` keeps the direct Workspace-private target path and Workspace-scoped package/tooling caches to avoid widening its reduced authority. Stronger immutability would require a separate snapshot or isolation design and its merge-back cost; it is not claimed here.

Workspace file observation has a separate path-authority boundary from source-state commitment. `workspace.read` and `workspace.content` open the Workspace root with `O_NOFOLLOW`, then use Linux `openat2` relative to that directory descriptor with `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS` and a no-follow final component. Metadata, bounded byte reads, digests, UTF-8 decoding, and media checks operate on that already-opened file descriptor rather than reopening a previously canonicalized pathname. This closes the demonstrated race where a same-authority process could replace a checked file with a symlink between `canonicalize` and `read`. Relative parent symlinks remain usable only when kernel resolution keeps them beneath the Workspace root. This hardening is currently a **read/observation** invariant; it does not claim that every Workspace write/mutation pathname has been converted to descriptor-relative mutation semantics.

## Optional external input ingress

External-file ingress is a distinct optional MCP adapter, not an extension of ordinary `InputAuthority` write authority. `ORDIVON_INPUT_INGRESS_JSON` separately names the authorities that may receive external files, an operator-private staging root, the Workstation ingress tool/configuration, allowed HTTPS download hosts, and a byte ceiling. `input.ingest` advertises OpenAI host file-parameter metadata only when this configuration exists. Runtime never persists or forwards the temporary signed download URL, verifies `expectedSha256` before Workstation delegation, and projects host-provided `fileId` only as unverified source identity. Workstation owns final digest-fenced/no-overwrite materialization; Runtime later remains an independent digest consumer through `workspace.execBound`. `runtime.describe` exposes only the ingress-enabled authority names, never staging paths, download hosts, or Workstation configuration paths.

The adapter is default-deny in two independent dimensions: a named authority in `ORDIVON_INPUT_AUTHORITIES_JSON` remains consume-only unless it is separately present in the ingress configuration, and an external download is accepted only under the configured HTTPS host policy. `downloadHosts` may list exact lowercase hostnames or the explicit `*` sentinel. `*` relaxes only the hostname-name match because host-issued file URLs have no durable public hostname contract; it does not relax HTTPS/443, no-proxy transport, per-hop DNS pinning, redirect revalidation, or rejection of loopback, private, link-local, unique-local, CGNAT, documentation, multicast, and other non-public addresses. This is a transport/materialization boundary, not Artifact acceptance, provider-identity proof, or a generic downloader.

## Encrypted credential delivery

Credential delivery is deliberately separate from immutable artifact input. `ORDIVON_CREDENTIAL_AUTHORITIES_JSON` configures operator-owned named roots plus an explicit non-empty `allowedPrincipals` set. Public requests contain only `{authority, credential}`; the Runtime-authenticated principal is checked before the credential object is resolved, so an unauthorized caller cannot use object existence or digest mismatch as a credential oracle. `runtime.describe` exposes authority names only, never host roots or ACL members.

An authority object is already a systemd-encrypted credential blob. On new admission Runtime copies that ciphertext into private staging, computes one canonical ciphertext-manifest digest as `credentialSetId`, commits only that set identity in the execution plan, and adopts the prepared directory into Job ownership. Runtime does not persist credential plaintext, a plaintext digest, the authority root, the authority ACL, or an additional per-credential binding record in the execution plan. Caller-authored command arguments remain ordinary operation truth and are not redacted automatically.

Linux trusted-local dispatch verifies the Job-owned ciphertext manifest and passes each member to systemd through `LoadCredentialEncrypted=`. systemd decrypts the credential and provides the standard `CREDENTIALS_DIRECTORY` process environment. Runner still clears the ambient host environment; it propagates only this systemd-owned capability pointer into the target after applying the frozen execution environment, so a caller cannot replace it with an arbitrary path. Credential delivery is rejected for `contained_local` and Windows-native execution in this contract.

Encrypted credential bytes are execution capabilities rather than historical evidence. Startup and periodic maintenance reconciliation retain them only while the owning Job is unresolved; durable Job resolution is sufficient authority to remove prepared or Job-owned ciphertext without a time-based retention policy. Exact replay uses Registry Job/Attempt/result truth and therefore does not require reopening a rotated CredentialAuthority or retaining the old encrypted blob. Missing ciphertext for an unresolved executable Job is reconciliation-required rather than permission to silently fetch the current credential version.

## Execution authority profiles

On a new admission, only after exact existing-Job replay has failed to resolve historical truth, Runtime compiles the existing public execution family into an internal `AuthorityContract`: ordinary execution, immutable-input reduced authority, immutable-input trusted authority, or credential-bound trusted authority. The contract binds the authenticated principal, target/profile, effective Windows context when applicable, executable identity paths, named input/credential authorities, and declared Host Dependency commitments, and rejects widening combinations fail-closed. This is Runtime admission truth only: it is not a caller-facing universal Authority object, a Security Grant, provider IAM, or a domain verdict, and R07 changes no public MCP Tool schema.

`workspace.exec` and `workspace.execPlan` accept `executionProfile` with two values. `workspace.execBound` does not expose this choice: the target determines the reduced-authority input boundary. `local_linux` uses `contained_local`; configured `windows_native` uses `trusted_local` with `windowsAuthority=limited`. `workspace.execBoundTrusted` is a separate local-Linux-only operation identity that structurally selects `trusted_local` while retaining the same exact named-authority input materialization and read-only `/run/ordivon/inputs` presentation. It deliberately preserves ambient trusted-local host/network authority and therefore must not be described as containment, controlled egress, a secret broker, or proof of external provider permission. Elevated Windows input-bound admission remains rejected.

- `trusted_local` is the canonical owner-trusted profile. It grants the installed service user's local authority without adding a central approval layer.
- `contained_local` is explicit and never silently falls back. Runtime uses the same systemd transient-unit supervisor, but sets a private network, removes effective and ambient capabilities, enables no-new-privileges, restricts namespaces and address families, makes the base filesystem read-only, hides `/root`, `/home`, `/run`, and `/var`, and bind-mounts back only the exact Runner, Git common directory, Workspace, Attempt bundle, and Runtime-created cache paths required by the committed plan. The Runner receives a fixed environment allowlist plus `GIT_OPTIONAL_LOCKS=0`; request environment is passed only to the target process through the durable Runner request.

This profile protects accidental credential and host-state access by local engineering workloads. It deliberately does not claim kernel-grade isolation against hostile same-host code, filesystem confidentiality outside the hidden state hierarchies, controlled egress, or disposable-machine semantics. Those belong to Edge or another external isolation owner. Dynamic users, bubblewrap, generic proxying, and policy-specific approval state are not part of contained v1 because they would duplicate supervision or introduce ownership and mount-composition costs without a demonstrated workload requirement.

## Execution budgets

Time and output bounds are always concrete in the durable Execution Plan. `ORDIVON_DEFAULT_RUNTIME_MS` defines the operator-owned Job timeout used only when an Agent-facing request omits `timeoutMs`; `ORDIVON_MAX_RUNTIME_MS` is the separate hard server ceiling for explicit Job timeouts, and `ORDIVON_MAX_OUTPUT_BYTES` remains the retained-output ceiling. If `ORDIVON_DEFAULT_RUNTIME_MS` is absent, Runtime preserves the historical compatibility behavior `default=max`; when it is configured, it must be positive and no greater than the maximum. Agent-facing `workspace.exec`, `workspace.execPlan`, `workspace.execBound`, and `workspace.execBoundTrusted` may omit the Job timeout, retained stdout/stderr limits, and step-local timeouts. Omission delegates only that mechanical constraint to Runtime: proposal identity preserves the omission, first admission resolves the Job timeout from the default policy and output limits from their current operator ceilings, and the resulting concrete values are frozen into the Execution Plan. Explicit timeout values are never silently clamped: they may exceed the default but a new admission above `ORDIVON_MAX_RUNTIME_MS` is rejected.

Current policy gates only new admission. Runtime performs idempotent existing-Job lookup before applying the current ceilings, so replay after a policy change returns the original Job and its original effective limits rather than recomputing or rejecting historical truth. `workspace.exec`, `workspace.execPlan`, `workspace.execBound`, and `workspace.execBoundTrusted` responses plus `job.observe` project those durable values as `effectiveLimits`. A structured plan's Job-wide timeout is one shared overall deadline; step-local timeouts are independent upper bounds and their arithmetic sum is not a Runtime law. The MCP adapter retains the previous fully explicit request shape and legacy request identity path; using any new optional/delegated limit semantics selects the proposal identity path.

Runtime does not hard-code a 24-hour/64-MiB product law. The packaged operator profile currently chooses a 1-hour default Job timeout and a 24-hour maximum, but another installation may deliberately choose a different valid pair without changing Runtime Core semantics. A caller may also commit optional positive physical budgets for memory, process count, and CPU quota. These values participate in the operation Digest and are applied by systemd to the Attempt cgroup through `MemoryMax=`, `TasksMax=`, and `CPUQuota=`. Runtime validates representability and positivity, while the operator and systemd/kernel own the actual resource policy. An empty budget is omitted from canonical serialization so requests admitted before this contract remain idempotently replayable.

Budgets constrain physical consumption; they are not a scheduler, priority system, sandbox, or approval policy. The trusted-local authority model remains unchanged.

## Execution provider commitment

First admission commits the Runtime-owned machinery that will cross the physical dispatch boundary. `local_linux` binds the validated Runtime Runner contract plus its executable SHA-256. `windows_native` binds the native Windows launcher contract plus its executable SHA-256. The persisted provider snapshot retains the historical `wslDistribution` field for old evidence, but new native snapshots write it as null. The snapshot is stored in an additive Job-owned Registry table and its digest is bound into the Job operation identity.

Dispatch re-observes the configured provider before bundle/target launch. An exact mismatch terminates the committed Attempt with `EXECUTION_PROVIDER_PRECONDITION_DRIFT` before a systemd unit or Windows child is created. For current provider-bound Linux Jobs, P3 additionally requires the running Runner to hash its actual `/proc/self/exe` into `runner-start.json`; Core requires that digest to equal the committed `local_linux_runner_v1` provider and, while systemd `MainPID` is still alive, independently hashes `/proc/<MainPID>/exe` and requires all three identities to agree. This closes the distinction between “the configured Runner path hashed correctly before launch” and “this is the image systemd actually started” without changing historical operation identity. A missing, extra, digest-mismatched, or contract-invalid side record is Registry corruption rather than a reason to reinterpret a provider-bound Job as historical. Jobs admitted before this contract have no provider commitment marker and preserve their historical behavior. Exact request replay is resolved before the current provider is inspected, so a terminal or already committed Job never becomes unreplayable merely because Runtime itself was upgraded later.

This commitment is deliberately narrow. It proves continuity of Runtime's own Linux Runner or Windows launcher and their declared dispatch contract; it does not by itself freeze shared libraries, kernel behavior, compiler/package closure, network responses, wall clock, external services, or the semantic contract of an arbitrary target command. P2 physically falsified one part of that boundary: the same dynamically linked target executable, with the same executable SHA-256 and the same prior operation identity, produced `ENV_V1` and `ENV_V2` after only its runtime-loaded shared library changed. Runtime therefore supports explicit `hostDependencies` for trusted-local Linux Jobs: each binding is an Agent-declared absolute regular non-symlink host file plus expected SHA-256, validated on new admission, stored as additive Job side truth, bound into `runtime-operation-v6`, and checked again before bundle dispatch. Empty bindings retain historical request and operation identities.

P3 then physically falsified the remaining pre-spawn claim. A real Runtime target passed every P2 check, printed `READY`, waited, and only afterward called `dlopen()` on a declared Host Dependency. Replacing that path between `READY` and `dlopen()` made the target consume V2 while P2 terminal evidence still named the committed V1 digest. Runner now establishes Linux inotify path/topology witnesses **before** its final Host Dependency digest validation, drains them before spawn, and keeps them active through the complete Attempt. Relevant file or ancestor-component write, metadata change, create/delete, rename/move, unmount/ignored watch, or queue overflow fails the Attempt as `HOST_DEPENDENCY_RUNTIME_DRIFT`; a terminal evidence record may state `hostDependencyContinuity=no_runtime_path_drift_observed` only when the Runner execution loop completed without such a witnessed event. This is a path-continuity witness, not a claim that the dependency was made immutable or that every possible consumption mechanism was intercepted.

The same validation-to-path-use problem exists for target executables. Runner establishes an executable path/topology witness before its final canonicalize/hash and keeps that witness active for the entire step. Runtime deliberately continues launching the original pathname: P3 proved that sealed memfd execution can force exact bytes but changes legitimate shebang `__file__`/`sys.argv[0]` and ELF `/proc/self/exe` semantics. A runtime executable pathname change therefore fails as `EXECUTABLE_RUNTIME_DRIFT` instead of silently changing execution, while normal target pathname semantics remain unchanged.

Host Dependency commitments are not an environment-image system and not automatic dependency discovery. Runtime cannot honestly infer every ELF loader edge, `dlopen`, Python/Node module, GPU driver, kernel facility, network service, or other ambient prerequisite. The Agent/domain declares prerequisites it knows materially define the physical action; Runtime makes those declarations identity-bound and witnesses ordinary Linux filesystem-path drift during the Attempt. P3 also physically rejected a single-file `BindReadOnlyPaths=snapshot:original` fix: replacing the parent-directory entry still made a delayed `dlopen()` resolve the new file. The current contract therefore says exactly what it can prove—no relevant path/topology drift was observed in Runtime's host namespace—not that the bytes were globally frozen or necessarily consumed by the target. P4 physically demonstrated the boundary: a `trusted_local` root target kept the host path on committed V1 while a private mount namespace bind made the same pathname resolve V2 inside the target; Runtime's host witness correctly saw no host-path event. Capability projection and terminal continuity evidence therefore name the scope `runtime_host_namespace_path_witness`. Same-authority mount/root-namespace reinterpretation, undeclared dependencies, and non-filesystem ambient state remain outside this claim. `contained_local` and Windows-native execution do not support Host Dependency commitments in this version.

## Windows-native execution target

`executionTarget` is orthogonal to `executionProfile`. `local_linux` remains the default and preserves the historical request-identity canonical form; `windows_native` is a distinct operation identity and is available only when the Runtime instance has explicit Windows provider configuration. It is not a third authority profile. R-W3 still admits one `trusted_local` Windows command at a time and structured multi-step plans remain Linux-only. `workspace.execBound` now also admits configured `windows_native` execution, but only under the default limited native authority; the Tool chooses the required trusted-local profile structurally and rejects elevated input-bound admission. Windows-native ordinary requests additionally expose `windowsAuthority=limited|elevated`; `limited` is the default. This field is target-specific requested authority, not an `ExecutionProfile`. Default limited requests retain the R-W2 canonical operation identity, while explicit `elevated` participates in operation/proposal identity and therefore cannot alias an existing limited Job.

Windows immutable-input admission reuses the same Agent/domain contract as Linux: named operator authority, relative object, exact SHA-256, and presentation-relative path. Runtime resolves and copies those bytes into its Job-owned input set before dispatch, so exact replay remains independent of later source-authority mutation or removal. The Windows launcher receives the Job-owned tree only as provider input, independently re-verifies the committed tree digest, and realizes an exact native copy at `%ProgramData%\OrdivonImmutableInputs\<inputSetId>`. The native tree contract includes the exact file set, directory closure, byte lengths, and file SHA-256 digests; reparse points, Win32-invalid names, reserved device aliases, and case-insensitive path collisions fail closed. The target receives only the native `ORDIVON_INPUT_ROOT`, not provider-private source/materialization paths.

The launcher protects the dedicated `OrdivonImmutableInputs` provider parent plus every native input directory and file with inheritance-disabled ACLs owned by Builtin Administrators: SYSTEM and Administrators retain Full Control while the committed limited user receives only ReadAndExecute. This parent protection is necessary: a physical pressure test proved that protecting only the input tree still let the limited user rename the whole committed root through inherited parent-directory authority. The final contract denies direct write/create/file-rename/ACL-grant, input-root rename, sibling creation, and presentation-container rename from the limited child. The launcher re-verifies the tree after staging, after publication, and after ACL application, and `windows-start.json` binds `inputSetId`, the native presentation root, and the exact input-tree digest to the Attempt. This is deliberately a **limited-child read-only boundary**, not a claim of immutability against a separate elevated administrator or other machine authority; explicit elevated input-bound requests are rejected. The native presentation is reconstructible provider-owned realization state and is currently retained rather than introducing an unproven cleanup/GC protocol into the execution path.

On a native Windows Runtime node, Runtime keeps the same durable Job/Attempt lifecycle while the operating-system owners change: Windows SCM owns daemon lifecycle and the repository-owned Windows launcher owns the Attempt process tree through a named Job Object. No Linux systemd unit, WSL interop socket, `\\wsl.localhost` projection, or WSL-mounted executable path participates in ordinary Windows dispatch. `windows-start.json` binds the Runtime Job/Attempt and launch-token digest to the Windows Job name, launcher/target process identity, process-creation FILETIME, exact image path, and image SHA-256 digest and is retained as a `windows_start` Artifact.

Direct native execution preserves the launcher's inner timeout and result as runner truth, while Core also enforces the committed outer deadline against the durable native launcher owner identity. Before requesting control action, Core durably changes the Attempt termination intent; termination is issued only against the exact recorded Windows launcher PID and process-creation identity. Identity mismatch fails closed, process disappearance alone is not completion evidence, and ambiguous pre-owner states are never silently redispatched.

Windows target commands do not inherit an ambient service or shell environment. On first admission, the configured launcher proves the requested `windowsAuthority`, obtains the corresponding native user/machine profile environment with inheritance disabled, projects only Runtime's mechanical allowlist, and freezes that baseline plus the Agent's explicit overlay into `RuntimeExecutionPlan`. `WindowsExecutionContext` records effective token class, user SID, environment-source contract, and privileged-broker binding when used. Exact replay returns the committed Job without re-reading current token or environment state.

`windowsAuthority=limited` must prove a primary, non-elevated, Medium-or-lower token for the committed user with Administrators not enabled. `windowsAuthority=elevated` is explicit selection of authority already exposed by the configured native provider; Runtime does not invoke UAC UI or acquire new machine authority. Requested and effective authority must agree before terminal commit.

The operator-owned Windows provider facts are native-only. `ORDIVON_WINDOWS_LAUNCHER_PATH` names the exact native launcher executable; optional privileged-broker configuration is likewise native Windows only. `ORDIVON_WINDOWS_WSL_DISTRIBUTION` is retired and is rejected if present. New execution-provider snapshots therefore record `wslDistribution=null`; the field remains in the persisted snapshot schema only so historical WSL-era Job evidence stays decodable and falsifiable.

The launcher applies Windows Job limits for committed job memory, active process count, and CPU rate. Windows accounting is target-native and is not claimed to be byte-for-byte identical to Linux cgroup accounting.

Every Runtime-mode Windows launcher acquires a Windows Power Request of type `SystemRequired` before native child start. The reason string is `Ordivon Runtime Attempt <attemptId>`, binding external observation to the physical Attempt. The lease is owned by launcher process lifetime, is cleared before a normal terminal result, and is released by process teardown on crash/cancel. Runtime does not globally alter user sleep/lid policy.

Native reconciliation is based on Windows launcher/Job Object owner evidence, not Linux supervisor identity. Runtime reconstruction reattaches the same durable Job/Attempt; missing or mismatched native owner evidence fails closed according to the committed termination intent. A Windows node remains independently available while WSL is stopped, and a Linux node can be offline without changing Windows Runtime authority.

The low-level launcher equipment proof remains `scripts/windows-job-launcher-acceptance.py`. Native-node acceptance and migration evidence are recorded in `RUNTIME_WINDOWS_R6C_ACCEPTANCE_R1.md`; the older WSL transport/restart experiments are historical evidence only and are no longer an executable Runtime path.
### Bound ownership rule

A Runtime bound must name the invariant it protects. Public page-size limits are acceptable when a stable cursor provides complete continuation; chunk/tail limits are acceptable when offsets or explicit truncation flags preserve recoverability; transport-body and retained-byte ceilings protect control-plane/resource envelopes; identifier and filesystem constraints protect durable addressing; containment rules protect isolation. Representation cardinality by itself is not a reason to reject Agent work. Accordingly, Runtime does not impose bootstrap-era maxima on argv count, environment count, `execPlan` steps, foreign references, mutation count, Patch file/edit count, or cgroup budget values. Individual argv/environment strings and their combined payload remain subject to the host Linux `execve` physical limits (`MAX_ARG_STRLEN` and `_SC_ARG_MAX`).

Static identifier constraints are part of the generated Tool input contract when JSON Schema can express them exactly. Workspace IDs use the Runtime's existing `1..96` ASCII addressing law. Environment keys use the executable environment-name pattern. Agent-authored logical labels—`clientRequestId`, step IDs, and foreign-reference namespace/type/id/generation/digest—are bounded by Unicode scalar count rather than UTF-8 encoding width: `1..256`, trimmed, control-free. Runtime-generated Job IDs are opaque returned handles and are not assigned a separate caller-created length law by `job.observe`. Content-dependent facts that cannot be proven statically, such as whether a UTF-8 scalar fits a requested byte chunk, remain structured runtime validation.

## Maintenance reconciliation

The service performs a low-frequency bounded reconciliation batch in addition to startup reconciliation. The batch prioritizes recovery-required and held-orphaned Attempts, then inspects other unsettled Attempts oldest first. Missed timer ticks are skipped rather than queued, and one batch never exceeds the configured bound. Agent-facing projection reads (`workspace.get`, `workspace.list`, and `job.list`) do not run reconciliation. `job.observe(jobId)` is the explicit targeted reconciliation path for one Job, while execution admission may reconcile the same Workspace before admitting new work.

This loop does not redispatch ambiguous work or retry failed commands. It only continues convergence among Registry state, runner evidence, and systemd/cgroup reality, including clearing recovery markers that became stale after a conclusive terminal result.

## Semantic health and Workspace lifecycle

`ordivon-runtime-doctor inspect` remains read-only and reports invariant violations, recovery cases, state counts, capacity holders, Artifact volume, and whether the Runtime is `healthy` or needs `attention`. Its defensive 50-holder diagnostic projection reports `capacityHoldersTruncated=true` when incomplete rather than silently presenting a prefix as complete. The summary explains current blocking facts; it does not invent a second control plane.

`workspace.get` distinguishes immutable lineage from live Git state: `sourceRevision` is the exact commit from which the Workspace was opened, while `currentHeadRevision` is the commit currently checked out at Workspace HEAD. It also exposes `sourceStateDigest`, the existing commitment over current HEAD, index flags and entries, tracked source bytes, untracked source bytes, file modes, symlinks, and nested Git worktrees. `workspace.list` carries the same opening/current revision distinction, uses a lightweight Git status probe, stable newest-first cursor pagination, and omits the expensive `sourceStateDigest` by default; callers may set `includeSourceStateDigest=true` when one page really needs exact digests. Healthy Workspace records are never silently discarded by the page-size limit, and inventory/projection failures remain explicit `issues`. Both operations are projection-only and do not reconcile or dispatch Jobs. `workspace.close.expectedSourceStateDigest` performs compare-and-close while holding the Runtime lifecycle lock; active or held Jobs block closure directly from durable reservation state without being dispatched by the close attempt. The same critical section also protects open Workspace Git authority: before deleting a Workspace directory or its disposable cache/build/tmp paths, Runtime resolves the actual Git common directory of every other open Workspace and rejects the close with `WORKSPACE_BUSY` when one depends on a path about to be removed. Because `workspace.open` holds the same lifecycle lock, concurrent open/close cannot race past that dependency fence. A mismatch fails without removal, while a successful close stores the exact digest in the tombstone so the same request can be replayed after response loss. This is a physical source-state fence only: Host remains responsible for deciding which evidence authorizes semantic completion.

Capacity admission remains immediate rather than creating a hidden queue. The production global limit is configurable and set to eight; one Workspace still owns at most one active execution. A `CONCURRENCY_LIMIT` error carries bounded holder Job and Workspace identities so callers can observe the actual occupants instead of polling blindly. The repository-owned `ordivon-runtime-capacity-acceptance` command verifies this contract through MCP by admitting exactly the configured capacity, rejecting the next Job, checking holder identity, observing terminal success, and cleaning every temporary Workspace.

The stronger compositional contract is that concurrent callers cannot turn the limit into an approximation. Admission commits the reservation in SQLite before dispatch; cancellation, natural completion, and recovery release it with the terminal state transaction; daemon reconstruction reads the same durable holders rather than resetting an in-memory counter. A rejected request has `commitState=not_started` and may retry the same identity after capacity is actually released.

Runtime deployment uses one release-artifact authority for the service binaries and installed Runtime-owned operator executables/support module. Release identity is owner-scoped: a standalone checkout has an empty owner prefix, while the modular monorepo uses `services/runtime`; an enclosing repository revision resolves to the latest commit at or before it that touched that owner. `prepare` builds and stages from a temporary detached checkout of that exact owner Commit rather than trusting mutable working-tree cleanliness, so sibling-owner commits and index flags cannot masquerade as Runtime source identity. The candidate/receipt binds the complete artifact set by digest and mode. For a nested owner, `plan` authorizes the required repository ref only when the candidate owner Commit is an ancestor of that ref and the Runtime owner subtree is byte-identical there; the plan exposes both the repository-level ref Commit and the resolved Runtime owner Commit. Standalone repositories retain exact-Commit required-ref semantics. Apply and rollback move the artifact set together, and a full release atomically compare-and-swaps the non-secret release authority (`ORDIVON_RELEASE_SOURCE_REPO` plus `ORDIVON_RELEASE_REQUIRED_REF`) together with Runtime-owned timeout policy. The deployment receipt records previous and candidate authority so post-commit failure or explicit rollback restores that environment state along with the previous artifacts instead of leaving source authority pointing at a release that is no longer installed. Status verifies the installed set against the latest successful release-state event, including a later explicit rollback. A rollback inherits `previousCommit` only when the pre-deployment complete artifact fingerprint matched an earlier receipted release; otherwise the restored bytes and modes remain exact while the source Commit is explicitly unknown. Schema-v1 binary-only receipts remain rollback-readable without making them the current release model.

When `ORDIVON_RELEASE_SOURCE_REPO` configures operator-owned self-release authority, it names the canonical Runtime owner directory rather than necessarily the Git top-level. The bound Workspace still names the enclosing Git-root snapshot, while the release request binds the owner-scoped Runtime Commit resolved from that snapshot. `ORDIVON_RELEASE_REQUIRED_REF` remains repository-level publication authority, but nested-owner authorization is proved through ancestry plus owner-tree equality rather than requiring unrelated sibling commits to share the Runtime Commit identity. These two release-authority settings are deployment state owned by the full release transaction, not an out-of-band precondition edited before binaries are replaced. The MCP surface adds the first structured external-effect contract rather than teaching arbitrary execution about effects. `release.apply` binds the Agent's exact Commit/candidate-manifest expectation to a server-derived candidate directory, candidate deployer executable, install/Registry/environment/receipt authority, and a deterministic effect receipt. The binding is additive Job side truth and advances new release operations to `runtime-operation-v5` without changing historical Execution Plan JSON or Registry migration version. Exact replay occurs before current release-world checks. `release.get` is projection-only and treats the canonical deployment receipt as stronger evidence of external release occurrence than generic process state. Explicit rollback remains the existing operator action; Runtime does not infer that rollback is the Agent's strategy.

Runtime-owned operator scripts do not interpret the Registry schema independently. `ordivon-runtime-reclaim`, `ordivon-runtime-deploy`, `ordivon-runtime-lifecycle`, `ordivon-runtime-cache`, and `ordivon-runtime-status` consume narrow read-only projections from `ordivon-runtime-inspect`; the repository-only archival planner uses the same boundary. Registry capability checks, active/held ownership, last-activity calculation, cache activity markers, health/dashboard Job projection, and cold-history classification therefore remain Rust Core semantics rather than duplicated Python SQL. `ordivon-runtime-reclaim apply` remains the only Workspace release executor and can archive old `stale_record` identities or release old `closable` Workspaces only through `workspace.close`. `ordivon-runtime-lifecycle` adds configured `ephemeral`, `review`, and `pinned` retention classes, uses the Runtime-projected latest durable Job/Attempt activity as the lease basis, and drives a receipted daily timer. Active, dirty, pinned, unknown, and orphan-directory cases are never automatic. Exact source-repository aliases can repair renamed Git worktrees; an explicitly confirmed quarantine path preserves unrepairable bytes and writes a closed tombstone. `workspace.close` removes that Workspace's disposable temporary, generic, Workspace-scoped compiled-build, and tmp caches before the physical worktree removal and tombstone commit, so a cleanup failure cannot be misreported after closure has committed. Global trusted-local package-download caches survive individual Workspace closure because they are reusable infrastructure rather than Workspace identity; legacy source-scoped build caches are reclaim-only leftovers, not active execution targets, and open Workspaces therefore do not protect them from capacity reclamation. Direct SQLite ownership remains only in the physical backup/restore utilities, where SQLite backup and integrity verification are the operation itself rather than Runtime-state interpretation. Deployment, lifecycle, hygiene, and rollback contracts are documented in [`operations.md`](operations.md).

## Completion and experience semantics

The Runtime uses five separate terms rather than one overloaded notion of completion:

- **Execution completion**: an Attempt has conclusive terminal execution evidence.
- **State convergence**: the Job has a resolution, every relevant Attempt is terminal, reservations are released, and no recovery condition remains active.
- **Client reattachment**: a caller reconnects to the same durable Job through its Job identity. Transport disconnects are not Attempt states.
- **Workspace closure**: the Git Workspace is independently proven closable and is removed through `workspace.close`, with rescue-ref and tombstone semantics.
- **Semantic completion**: an Agent or human concludes that the user's actual objective is satisfied. The Runtime does not adjudicate this claim.

A successful process exit is execution evidence, not proof of semantic completion. An Artifact is retained evidence, not proof that a claim is correct. A closed Workspace does not change Job resolution, and client reconnection does not change Attempt state.

## Mechanical acceleration measurements

`ordivon-runtime-inspect summary` derives mechanical latency distributions from the existing append-only Job event history. It reports admission-to-dispatch, dispatch-to-Runner binding, Runner-binding-to-terminal, cancellation-to-terminal, and reconciliation-failure-to-convergence intervals alongside total Job duration, recovery, duplicate-dispatch, cancellation, and Artifact facts. No timing table, telemetry service, or semantic score is added. Missing event pairs produce zero samples rather than invented timings. These measurements expose Runtime's physical contribution to a wider `verified improvement / unit time` evaluation; they do not decide whether the executed work was useful or correct.

## Correlated Job lookup

`job.list` retains newest-first cursor pagination and may additionally filter by an exact `workspaceId`, `clientRequestId`, or their intersection. The filters are projection-only reads over the durable Job Registry and indexed identities; `job.list` does not reconcile or dispatch Jobs and therefore cannot advance unrelated work as a side effect of reattachment. Recovery callers still consume every filtered page and reject conflicting Job identities rather than treating the newest match as sufficient proof. When the Agent needs fresher physical state, it targets one exact Job with `job.observe`, which may reconcile or dispatch that already-admitted Job but does not scan unrelated Jobs. The lookup indexes are maintained idempotently as non-semantic query capabilities rather than advancing the Registry schema version, so the previous Runtime binary can still open the same Registry during receipt-bound rollback. This maintenance includes `idx_artifacts_job` on `artifacts(job_id)`: Job-level Artifact volume is part of the stable Agent-facing `job.get`/`job.list` projection, but the index itself is reconstructible mechanical acceleration rather than durable semantic truth. Keeping it outside schema migrations prevents a performance-only change from closing the receipt-bound previous-binary rollback window. Status health also maintains narrow reconstructible `jobs(resolution)` and `attempts(recovery_required)` indexes so active/recovery counts do not scan historical Job payload rows as the Registry grows. These remain query accelerators rather than durable schema truth.

There is intentionally no claim that `job.observe` is a pure read: it may advance reconciliation for the targeted durable Job. `job.get` is the exact non-reconciling `jobId` projection and reuses Runtime Core's read-only inspection truth rather than duplicating Job query semantics in MCP. Its public timeline is bounded by `eventLimit`, omits unbounded event detail, and leaves retained stdout/stderr/results behind `artifact.read`; operator-local inspection may still request forensic event detail. `job.list` remains the paginated non-reconciling discovery/reattachment projection when the exact Job identity is not yet known.

## Read-only experience projection

The append-only Runtime Registry remains the only physical execution-fact database for Runtime Jobs and Attempts. `ordivon-runtime-inspect` derives bounded reports without adding tables, events, or a second history store:

```text
ordivon-runtime-inspect job --database <registry> --job-id <job> --pretty
ordivon-runtime-inspect workspace --database <registry> --store-root <runtime-store> --workspace-id <workspace> --pretty
ordivon-runtime-inspect summary --database <registry> --since-ms <unix-ms> --pretty

# Narrow operator-only Registry projections used by maintenance wrappers:
ordivon-runtime-inspect registry --database <registry>
ordivon-runtime-inspect registry-workspace --database <registry> --workspace-id <workspace>
ordivon-runtime-inspect registry-activity --database <registry>
ordivon-runtime-inspect registry-markers --database <registry> [--workspace-id <workspace>]
ordivon-runtime-inspect registry-status --database <registry> --job-limit 5
ordivon-runtime-inspect registry-archive --database <registry> --cutoff-ms <unix-ms> --sample-limit 20
```

The Job report projects Attempts, reservations, conditions, Artifact volume, recovery/cancellation episodes, and a bounded event timeline. The Workspace report combines current Git HEAD/status with complete active-Job identities and a bounded recent-Job projection including Attempt state, execution disposition, recovery requirement, duration, Runner progress/current step, last output activity, and Artifact count. Operator-only Registry projections expose only the facts required by deployment, lifecycle, cache, status, reclaim, and archival planning, so those Python wrappers no longer carry their own Registry SQL or schema interpretation. Registry-backed inspection uses query-only SQLite reads owned by Runtime Core; Git and filesystem facts remain separate physical observations rather than pretending to be one cross-owner transaction. A bounded inspection validates the capabilities it actually consumes and fails on SQLite/query/row-decoding errors that it encounters, but it deliberately does **not** run whole-database integrity scans. Full-database page and foreign-key integrity are distinct operator health claims owned by `ordivon-runtime-doctor` and the physical backup/restore paths. Runtime initialization remains fail-closed on SQLite open/configuration errors, migration version/checksum drift, required schema/index/storage presence, and WAL/foreign-key enforcement, but it does not scan historical Registry pages before binding the MCP service. This keeps startup availability and exact projections proportional to their requested boundary instead of making historical Registry size part of every process restart. Inspection never calls `job.observe` or reconciliation. The summary reports mechanical convergence, resolutions, recovery convergence, duplicate physical dispatch, cancellation outcomes, duration percentiles, Artifact volume, and terminal reasons. None of these reports evaluates semantic completion.

These metrics are diagnostic references for Runtime changes. They do not score model reasoning, user satisfaction, context quality, or user rework, and they do not create a new MCP tool.

## MCP protocol boundary

The Adapter uses the stable MCP `2026-07-28` stateless lifecycle as its canonical path and currently retains compatibility lifecycles `2025-11-25` and `2025-06-18` on the same HTTP endpoint. Modern requests use `server/discover`, standard routing headers, and per-request metadata without a protocol Session. `LocalSessionManager` exists only for legacy `initialize` clients; Runtime continuity remains the durable Workspace/Job/Attempt model in Core.

The MCP HTTP request body remains bounded to `ORDIVON_BODY_LIMIT_BYTES` (1 MiB in production). This is a control-plane envelope, not a large-object transport: scalar arguments remain inline, while future source replacements above that envelope require digest-bound Artifact or stdin input rather than larger argv values or an unbounded HTTP body.

Omitting `waitMs` on public execution admission performs only a brief 2-second observation after the durable Job exists; explicit callers may still request longer waits up to the existing Core maximum. This keeps the normal MCP request lifecycle shorter than long-running execution while preserving the same durable Job/Attempt identity for later `job.observe`. systemd launch/cancel commands are submitted with `--no-block` after the corresponding Runtime intent is durable; Runner launch evidence, process identity, terminal evidence, and reconciliation remain physical truth.

Workspace reads distinguish response bounds from proof cost. FULL reads hard-cap bytes actually consumed. SLICE reads keep memory proportional to the requested slice plus a fixed streaming buffer while still validating and hashing the whole file in one pass; therefore SLICE I/O remains O(file size) because the public result still includes a whole-file digest. `workspace.diff.maxBytes` is narrower: it bounds retained diff text, and Runtime now stops the Git child after observing one byte beyond that budget instead of materializing complete diff stdout first. Its historical structured changed/modified/added/deleted/renamed/untracked arrays remain complete and therefore are intentionally not response-bounded.

`workspace.changes` is the response-bounded structured surface for large change sets, and Runtime retains only a bounded candidate/page set while producing it. Each page returns one atomic entry stream (`modified`, `added`, `deleted`, or `untracked`), with `limit` bounding entry count and `maxBytes` bounding the encoded entry payload. Runtime asks Git for exact path/kind truth, derives an order-independent `changeSetDigest`, orders continuation by the canonical `(path, kind)` order rather than Git emission order, and returns `nextCursor={changeSetDigest, afterPath, afterKind}` when more entries remain. The cursor is valid only while the projected change membership/kinds are unchanged, and `afterPath`/`afterKind` must name a real member of that set. Byte changes inside an already-`modified` or already-`untracked` path intentionally do not invalidate continuation because this Tool proves the structured change set rather than source bytes; callers that require exact byte identity use `workspace.get.sourceStateDigest` or file digests.

Rename/copy similarity detection is intentionally disabled on this scalable projection: a rename is represented as one deleted path plus one added path. `workspace.diff` remains the richer compatibility surface when rename interpretation is worth its extra Git analysis cost. Git's exhaustive rename/copy fallback can become quadratic in the number of unmatched sources/destinations, which is the wrong hidden default for the large-change-set path.

The Tool does not claim O(page) discovery work. Without a separate maintained change index or snapshot, Git must still enumerate the current change metadata to establish the page and its continuation fingerprint; Runtime performs a second exact change-set scan to reject a transition during one page projection. Work is therefore O(current change count) per page while response size and Runtime-owned retained entry memory remain bounded. Exact Git change detection may still read changed file bytes and the Git child process's I/O/RSS can scale with changed file size; `maxBytes` is not a Git resource budget. The public MCP default remains 64 entries, while callers may raise `limit` up to 1024 under the same `maxBytes` response budget after inspecting `totalEntries` and `remainingEntries`. A persistent change/content index would create a new state owner and is not justified until real workloads show that discovery cost, rather than response size, is the bottleneck.

Executable identity also separates invocation semantics from target authority. Runtime requires an absolute invocation path, requires both the invocation location and canonical target to remain inside configured executable roots, validates the target SHA-256, persists the invocation path, and Runner executes the verified target with the original invocation restored as `argv[0]`. This preserves rustup-style multicall/proxy behavior without allowing a symlink retarget to bypass executable verification.

`server/discover` returns a deterministic SHA-256 `toolCatalogDigest` over the complete name-sorted Tool definitions with `ttlMs=0` and private cache scope. Deployment receipts bind this digest. Every public Tool publishes both its generated input schema and a structured `outputSchema`; the output contract is the union of the exact success result and the standard `{ "error": ToolError }` envelope, whose `origin`, `retryClass`, and `commitState` values are finite machine-readable vocabularies. `workspace.exec` exposes Core's typed execution proposal directly: MCP decides only whether an all-explicit legacy request must preserve its v1 identity shape or whether the request uses proposal semantics. `workspace.execBound` is a separate versioned admission Tool: it adds exact named-authority input commitments, structurally selects the target's reduced-authority contract (`contained_local` for Linux; `trusted_local` plus limited native authority for Windows), and uses proposal-plus-input request identity while reusing the same Job/Attempt/Artifact lifecycle. `workspace.execBoundTrusted` reuses the same Core input identity/materialization machinery under a distinct public operation identity but structurally selects `trusted_local` on local Linux so trusted provider adapters can retain ordinary process-scoped network access while consuming exact immutable bytes. `workspace.execCredentialBoundTrusted` is a separate local-Linux trusted operation identity whose public credential schema is only `{authority, credential}`; Core binds the authenticated principal, CredentialAuthority authorization, ciphertext snapshot identity, replay behavior, and terminal reclamation while systemd owns decryption and process delivery. Immutable-input roots come from `ORDIVON_INPUT_AUTHORITIES_JSON`; encrypted credential roots and their principal ACLs come from `ORDIVON_CREDENTIAL_AUTHORITIES_JSON`; callers never submit either host root. Core owns proposal canonicalization, policy resolution, idempotent replay, materialization, and effective-plan truth. The Adapter no longer advertises or implements the experimental Core Tasks methods (`tasks/list`, enqueue, get, result, cancel). Execution Tools return Ordivon Job observations, while `job.observe`, `job.list`, and `job.cancel` remain ordinary Tools. MCP adapts transport and discovery; it does not become Runtime's persistence model.

Runtime trace JSONL files rotate at 64 MiB and retain one previous segment. Rotation and append are serialized by one process-local mutex so concurrent MCP requests cannot race the rename/open sequence. `scripts/ordivon-runtime-status` scans the current and rotated segments within its existing bounded byte budget, and projects a compatibility inventory from the current deployment receipt, recent protocol observations, and the immediately previous receipted deployment. Every retained protocol version therefore names a current production, live-client, or rollback consumer plus a deletion trigger. Missing, truncated, or not-yet-long-enough trace evidence blocks deletion conclusions but does not make Runtime unhealthy. The complete inventory, including persisted-state compatibility, is defined in [`compatibility.md`](compatibility.md).

## Extension boundary

Use existing host executables through `workspace.exec` unless repeated real use proves that a stable operation needs a dedicated structured Tool contract. Arbitrary execution is effect-opaque and may interact with an open world of external entities: a caller may not promote it to read-only, idempotent, closed-world, or reconcilable by declaration. A structured effect adapter is justified only when it owns canonical identity, enforceable preconditions, receipt or state proof, reconciliation, and ambiguity behavior. `contained_local` reduces ambient local authority for ordinary engineering workloads; genuinely hostile, multi-tenant, controlled-egress, or disposable workloads still require an external isolation boundary owned outside Runtime.
